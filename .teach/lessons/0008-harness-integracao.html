Testar a API inteira, contra um banco de verdade

Aula 08 · Fatia 8 do Ticket 01 · WebApplicationFactory + Testcontainers · última fatia da fundação

Vitória desta aula: entender a diferença entre teste unit e teste de integração, e montar o harness que sobe o Program.cs inteiro apontado para um Postgres real e descartável — a base sobre a qual toda fatia de negócio (02+) vai ganhar teste verde de graça.

1. Unit vs integração

  • Unit: testa uma classe isolada, sem framework, sem banco. Rápido, mas não prova que as peças se encaixam.
  • Integração: sobe a aplicação inteira — DI, pipeline MediatR, EF Core, migration, banco — e exercita de fora. Prova que o conjunto funciona.

Regra do projeto: negócio se testa por integração. Se o handler grava no Postgres e lê de volta o jsonb certo, confiamos. Nada de mockar EF.

2. WebApplicationFactory<Program>

Do pacote Microsoft.AspNetCore.Mvc.Testing. Ele instancia o seu Program.cs em memória (sem abrir porta de rede) e te dá um HttpClient que fala com a API como um cliente real — além de acesso à mesma IServiceProvider (a DI de produção). 

// no fim do Program.cs:
public partial class Program;
Por que esse partial? Top-level statements (o Program.cs sem class explícita) geram um Program internal. O teste precisa referenciar o tipo em WebApplicationFactory<Program> — o public partial class Program; só o torna visível. Uma linha, zero lógica.

3. Testcontainers: Postgres real e descartável

Poderíamos apontar para SQLite em memória — mas aí não é o mesmo banco: sem jsonb, sem os defaults, sem o Npgsql. Testcontainers sobe um Postgres de verdade em Docker só para o teste e joga fora no fim. Mesmo provider, mesma migration que roda em produção. 

private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder()
    .WithImage("postgres:16-alpine")
    .Build();

4. Costurando os dois (a fábrica)

protected override void ConfigureWebHost(IWebHostBuilder builder)
{
    // troca só a connection string; a DI de produção fica intacta
    builder.UseSetting("ConnectionStrings:Default", _postgres.GetConnectionString());
}

async Task IAsyncLifetime.InitializeAsync()
{
    await _postgres.StartAsync();                 // 1. sobe o container
    using var scope = Services.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<PensaComigoDbContext>();
    await db.Database.MigrateAsync();             // 2. aplica a migration nele
}

AddPersistence lê GetConnectionString("Default") só na hora de construir o DbContext — então basta sobrescrever a setting antes do build. Não mexemos na DI real; só desviamos o alvo. IAsyncLifetime é o gancho do xunit: InitializeAsync roda antes dos testes, e o par DisposeAsync destrói o container depois.

Detalhe que mordeu no caminho: o xunit v2 declara IAsyncLifetime com retorno Task, mas a base WebApplicationFactory já tem um DisposeAsync que retorna ValueTask. Dois DisposeAsync com assinatura diferente colidem. Solução: implementar a interface explicitamente (async Task IAsyncLifetime.DisposeAsync()) — cada lado fica com o seu.

5. O smoke test que prova a fundação

public class SpineSmokeTests(PensaComigoApiFactory factory)
    : IClassFixture<PensaComigoApiFactory>
{
    [Fact]
    public async Task Migration_aplica_e_seed_de_usuarios_esta_presente()
    {
        using var scope = factory.Services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<PensaComigoDbContext>();
        var nomes = await db.Usuarios.Select(u => u.Nome).ToListAsync();
        Assert.Contains("Antonio Ramon", nomes);
    }
}

IClassFixture faz o xunit criar uma fábrica compartilhada por toda a classe (um container, não um por teste). Este teste toca a migration + o seed de ponta a ponta: se ele passa, a fundação está de pé.

Pré-requisito: Testcontainers precisa de Docker rodando. Sem Docker Desktop no ar, o teste não executa (o código compila igual). É passo de infra seu — como foi o database update no Supabase.
