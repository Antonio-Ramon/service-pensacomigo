2. IFormFile e o [Consumes]

[HttpPost]
[Consumes("multipart/form-data")]                 sem isso o Swagger manda JSON e dá 415
[RequestSizeLimit(ImagensPermitidas.TamanhoMaximoBytes)]
public async Task<ActionResult<ImagemResponse>> Enviar(IFormFile arquivo, CancellationToken ct)

multipart/form-data é o formato do <input type="file">: o corpo vem picotado em partes, cada uma com nome e cabeçalhos próprios. O ASP.NET casa a parte chamada arquivo com o parâmetro arquivo — o nome do parâmetro é o contrato. E os dois atributos fazem coisas diferentes:

  • [Consumes] — declara o content-type aceito. Serve pro model binder e pro Swagger gerar o botão de escolher arquivo em vez de uma caixa de JSON.
  • [RequestSizeLimit] — corta o request no servidor, antes de você. O validator também barra 5 MB, mas só depois de o corpo inteiro subir. Os dois existem por motivos diferentes: o atributo protege a máquina, o validator dá a mensagem amigável.

3. Onde o ASP.NET para de existir

await using var conteudo = arquivo.OpenReadStream();
var command = new EnviarImagemCommand(usuarioId, arquivo.FileName, arquivo.Length, conteudo);

IFormFile vive em Microsoft.AspNetCore.Http — é um tipo de web. Se ele entrasse no Command, a Application passaria a depender do ASP.NET e o caso de uso só existiria dentro de um request HTTP. Por isso o controller desmonta o IFormFile em três coisas que qualquer host sabe fornecer: nome, tamanho e Stream. Mesmo movimento das Fatias 10 e 14 — a fronteira é o controller.

Stream, não byte[]: byte[] materializa o arquivo inteiro na memória do servidor. 20 autores publicando ao mesmo tempo = 100 MB de heap, e o coletor de lixo do .NET manda blocos acima de 85 KB direto pro Large Object Heap, que fragmenta e quase não é compactado. Com Stream, os bytes chegam do Kestrel e saem pro Supabase em pedaços — a memória fica constante.

E o await using? É o using assíncrono: chama DisposeAsync() ao sair do escopo, fechando o stream mesmo se der exceção no meio. Todo Stream merece um.

4. O content-type sai da whitelist, não do cliente

public static readonly Dictionary<string, string> Tipos = new()
{
    [".jpg"] = "image/jpeg", [".jpeg"] = "image/jpeg",
    [".png"] = "image/png",  [".webp"] = "image/webp",
};

O multipart traz um Content-Type declarado pelo cliente. Ele é ignorado. O handler deriva o tipo da extensão, que já passou pela whitelist do validator. Motivo concreto: o storage devolve o arquivo com o content-type que recebeu — um ".png" gravado como text/html vira uma página HTML hospedada no seu domínio, executando script no navegador de quem abrir. Isso é XSS, e a defesa é uma linha: o tipo vem da nossa tabela.

A mesma classe guarda o limite de tamanho, e é ela que o validator, o handler e o atributo do controller consultam. Uma whitelist, três consumidores, zero chance de divergirem.

5. ICommand agora, IQuery antes

Na versão signed URL o caso de uso era IQuery — "não grava no nosso Postgres". Agora é ICommand. O critério que ficou: 

tem efeito colateral no mundo?  →  ICommand      gravar bytes conta
só responde uma pergunta?       →  IQuery

"Mas o UnitOfWorkBehavior vai commitar o quê?" Nada: SaveChanges sem mudanças rastreadas não abre transação, não vai ao banco. O custo é zero e o nome fica honesto — quem lê EnviarImagemCommand sabe que algo mudou lá fora.

6. Testar upload sem servidor de arquivos

var arquivo = new ByteArrayContent(Encoding.UTF8.GetBytes("bytes-de-imagem"));
arquivo.Headers.ContentType = new MediaTypeHeaderValue("application/octet-stream");
return new MultipartFormDataContent { { arquivo, "arquivo", nomeArquivo } };
                                        ↑ conteúdo  ↑ nome do campo  ↑ nome do arquivo

O MultipartFormDataContent monta o corpo exatamente como o navegador. E repare no teste novo: ele afirma Assert.Equal("image/png", StorageFake.UltimoContentType) — o fake grava o que recebeu pra o teste provar que o content-type saiu da whitelist e não do multipart. Fake que só devolve valor testa o caminho feliz; fake que registra testa a decisão.
