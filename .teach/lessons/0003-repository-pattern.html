O contrato mora no Domain, o motor mora no Persistence

Aula 03 · Fatia 3 do Ticket 01 · Repository pattern, inversão de dependência e DI

Vitória desta aula: entender por que a interface do repositório fica no Domain e a implementação (que usa EF Core) fica no Persistence — e como a injeção de dependência costura as duas em runtime.

1. O problema que o pattern resolve

O caso de uso (Application) precisa buscar e gravar posts. Se ele chamasse dbContext.Posts.FirstOrDefault(...) direto, a Application ficaria amarrada ao EF Core. Trocar de ORM, ou testar sem banco, viraria um pesadelo. Clean Architecture proíbe isso: o núcleo não conhece infraestrutura.

2. Inversão de dependência (o "D" do SOLID)

A direção normal seria Application → Persistence (quem precisa aponta pra quem faz). Invertida, os dois apontam pra uma abstração no meio: 

Application  ─chama→  IPostRepository        (interface, no Domain)
                            ▲
Persistence  ─implementa┘   PostRepository    (classe, usa EF Core)

A seta de dependência do Persistence sobe pro Domain. O Domain não sabe que o EF existe — ele só define o quê (o contrato). O Persistence decide como.

3. As duas metades

a) O contrato — Domain/Repositories/IPostRepository.cs

public interface IPostRepository
{
    Task<Post?> ObterPorIdAsync(Guid id, CancellationToken ct = default);
    Task AdicionarAsync(Post post, CancellationToken ct = default);
}

Nada de EF aqui — só tipos do Domain. Note o ? em Post?: "pode não achar". E CancellationToken, padrão em todo método async .NET (deixa o request abortar a query se o cliente desistir).

b) O motor — Persistence/Repositories/PostRepository.cs

public class PostRepository(PensaComigoDbContext db) : IPostRepository
{
    public Task<Post?> ObterPorIdAsync(Guid id, CancellationToken ct = default) =>
        db.Posts.FirstOrDefaultAsync(p => p.Id == id, ct);

    public async Task AdicionarAsync(Post post, CancellationToken ct = default) =>
        await db.Posts.AddAsync(post, ct);
}
AdicionarAsync não chama SaveChanges. Ele só rastreia o objeto. Quem grava de fato é o UnitOfWorkBehavior (Fatia 5), num commit atômico por comando. Repositório junta a intenção; UnitOfWork fecha a transação.

PostRepository(PensaComigoDbContext db) é primary constructor (C# 12): o parâmetro db vira campo utilizável no corpo, sem boilerplate. De onde vem esse db? Da DI — próximo ponto.

4. Injeção de dependência (DI)

Ninguém dá new PostRepository(...) na mão. Você registra o mapa "interface → implementação" no container, e ele constrói tudo pra você: 

// Persistence/DependencyInjection.cs
services.AddScoped<IPostRepository, PostRepository>();

Quando algo pedir IPostRepository no construtor, o container cria um PostRepository e injeta o DbContext que ele precisa — recursivamente. AddScoped = uma instância por request HTTP (o tempo de vida certo pra DbContext).

Tudo fica numa extension method AddPersistence(), então o Program.cs só faz builder.Services.AddPersistence(); — a fiação mora na camada dona dela, não vaza pro host.
