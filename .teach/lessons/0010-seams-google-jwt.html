O trem completo: implementando os seams

Aula 10 · Fatia 10 · Ticket 02 (Auth) · das interfaces às implementações reais

Vitória desta aula: o login agora roda de ponta a ponta. Na Aula 09 o handler dependia de duas interfaces vazias. Hoje você escreve as duas classes que faltavam, registra na DI, e o trilho ganha o trem.

1. Onde a implementação de um seam vive?

A interface (IGoogleTokenValidator) mora na Application. A implementação não pode morar lá — ela usa Google.Apis.Auth, e a regra da Clean Architecture proíbe a Application de conhecer libs externas. Então a impl vai pra fora, no host Web (a "composition root"), pasta Web/Auth/. 

Application/Auth/IGoogleTokenValidator.cs   o contrato (a Application enxerga)
Web/Auth/GoogleTokenValidator.cs            a impl (só o host enxerga)

A seta de dependência aponta de fora (Web) pra dentro (Application) — nunca o contrário. Isso é inversão de dependência: o handler manda no contrato, o host escolhe o concreto. Não criamos um projeto Infrastructure separado — YAGNI: com um host só, o Web já é o lugar natural.

2. Validar o token do Google

public class GoogleTokenValidator(IConfiguration config) : IGoogleTokenValidator
{
    public async Task<GoogleUserInfo> ValidarAsync(string idToken, CancellationToken ct = default)
    {
        var settings = new GoogleJsonWebSignature.ValidationSettings
        {
            Audience = [config["Google:ClientId"]!],   o aud tem que ser NOSSO app
        };
        try {
            var p = await GoogleJsonWebSignature.ValidateAsync(idToken, settings);
            return new GoogleUserInfo(p.Email, p.Subject, p.Picture);
        }
        catch (InvalidJwtException) {
            throw new RegraDeNegocioException("Token do Google inválido ou expirado.");  → 422
        }
    }
}

A lib baixa as chaves públicas do Google e confere a assinatura — você não confia no conteúdo, confia na criptografia. Se o token for forjado, expirado, ou o aud não bater, ela lança InvalidJwtException, que traduzimos pra nossa exceção tipada da Aula 06.

3. Emitir o JWT PRÓPRIO

Depois do Google validar quem a pessoa é, nós emitimos nosso token — o que o frontend manda de volta em toda requisição. Assinamos com a mesma chave que o Program.cs valida desde a Aula 07: 

var chave = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(jwt["Key"]!));
var cred  = new SigningCredentials(chave, SecurityAlgorithms.HmacSha256);

Claim[] claims = [
    new(JwtRegisteredClaimNames.Sub, usuario.Id.ToString()),   quem é
    new(JwtRegisteredClaimNames.Email, usuario.Email),
    new("is_admin", usuario.IsAdmin.ToString()),               o que pode
];
var token = new JwtSecurityToken(jwt["Issuer"], jwt["Audience"], claims,
                                 expires: DateTime.UtcNow.AddHours(8), signingCredentials: cred);
return new JwtSecurityTokenHandler().WriteToken(token);
Dois tokens, não confunda: o idToken do Google prova a identidade UMA vez, no login. O JWT próprio é a sua sessão dali pra frente. O Google não sabe nada do seu app depois do login — daí a necessidade de emitir o seu.

Claims são afirmações assinadas sobre o portador. Como estão dentro da assinatura, ninguém as adultera sem invalidar o token. Na Fatia 11 você vai ler essas claims via User num endpoint [Authorize].

4. Ligar tudo na DI

builder.Services.AddScoped<IGoogleTokenValidator, GoogleTokenValidator>();
builder.Services.AddScoped<IJwtTokenGenerator, JwtTokenGenerator>();

Estas duas linhas são o que faltava. Agora quando o MediatR constrói o LoginGoogleCommandHandler, o container resolve as interfaces do construtor pras classes concretas. Sem elas o app subia mas explodia ao tentar montar o handler — a DI não saberia o que injetar.
