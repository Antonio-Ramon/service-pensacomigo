SignalR e eventos pós-commit

Aula 23 · Fatia 23 · Realtime de comentários — implementa o ADR 0001

Vitória desta aula: quem está com o post aberto vê o comentário do outro aparecer sozinho, sem F5 e sem polling. E — a parte difícil — o evento só sai depois que o INSERT entrou de verdade no Postgres.

1. Por que WebSocket nosso, e não o Realtime do Supabase

O Supabase oferece escutar a tabela direto do browser. Duas linhas de JS e pronto. O preço: o front passa a conhecer o schema do banco, e o anon key exposto obriga a ligar RLS em todas as tabelas — que hoje não existe, porque quem criou o schema foi o EF (migration InicialSchema, zero policies). Furaria a regra que vale desde a Fatia 1: tudo passa pela nossa API.

Decisão registrada no ADR 0001. Vale ler o ADR inteiro — ele é um exemplo de decisão de arquitetura que já foi revisada uma vez (a redação original descrevia uma ordem impossível; é exatamente o que a seção 3 desta aula desmonta).

2. SignalR em três peças

SignalR é nativo do ASP.NET Core — zero pacote novo. Ele te dá WebSocket com fallback automático (Server-Sent Events, long polling) para redes que bloqueiam WS, e reconexão do lado do cliente.

PeçaO que é
HubUma classe. Os métodos public dela são chamáveis pelo browser — é o "controller" do WebSocket.
GrupoUm nome (string) com uma lista de conexões. post:{id} → só quem abriu aquele post recebe.
IHubContextComo o resto do servidor empurra mensagem sem estar dentro de uma chamada do Hub.
public class ComentariosHub : Hub
{
    // chamado PELO cliente: connection.invoke("Entrar", postId)
    public Task Entrar(Guid postId) => Groups.AddToGroupAsync(Context.ConnectionId, Grupo(postId));
    public Task Sair(Guid postId)   => Groups.RemoveFromGroupAsync(Context.ConnectionId, Grupo(postId));

    public static string Grupo(Guid postId) => $"post:{postId}";
}
Sem [Authorize] no Hub, ao contrário do que a primeira versão do ADR imaginava. Comentário e curtida são anônimos por design neste projeto (Fatias 20 e 22). Exigir JWT no Hub deixaria o leitor sem realtime justamente no caso de uso que é dele.

3. O problema da ordem: o handler não commita

O reflexo é empurrar o evento no fim do handler. Olha o que isso seria: 

await comentarios.AdicionarAsync(comentario, ct);
await hub.Clients.Group(...).SendAsync("ComentarioCriado", resposta);  // ← ERRADO
return resposta;

AdicionarAsync só mexe no ChangeTracker. Nenhum INSERT saiu ainda — quem manda SaveChanges é o UnitOfWorkBehavior, que envolve o handler (Fatia 5): 

var resposta = await next(ct);   // ← o handler inteiro roda AQUI
await uow.CommitAsync(ct);       // ← o INSERT acontece AQUI
return resposta;

Ou seja: todo o corpo do handler é, por construção, pré-commit. Empurrar dali tem dois defeitos, nessa ordem de gravidade:

  1. O cliente recebe "tem comentário novo", refaz o GET e não acha nada — chegou antes do INSERT.
  2. Se o commit falhar, o grupo inteiro foi notificado de algo que nunca existiu.

4. A solução: enfileirar no handler, publicar na pipeline

O handler não publica; ele enfileira. Um buffer Scoped (vive uma requisição) guarda os eventos, e um behavior novo — registrado por fora do UnitOfWorkBehavior — drena a fila depois que o CommitAsync voltou. 

public class FilaDeEventos
{
    private readonly List<INotification> eventos = [];
    public void Adicionar(INotification evento) => eventos.Add(evento);
    public IReadOnlyList<INotification> Drenar() { var copia = eventos.ToArray(); eventos.Clear(); return copia; }
}
public class DespachoDeEventosBehavior<TRequest, TResponse>(FilaDeEventos fila, IPublisher publisher)
    : IPipelineBehavior<TRequest, TResponse> where TRequest : notnull
{
    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var resposta = await next(ct);          // inclui o CommitAsync do behavior de dentro

        foreach (var evento in fila.Drenar())   // só chega aqui se o commit não estourou
            await publisher.Publish(evento, ct);

        return resposta;
    }
}
Repare no que NÃO tem aqui: try/catch. Se o commit estourar, a exceção sobe e as linhas do foreach nunca rodam. A garantia "evento só depois do commit" é dada pela ausência de tratamento, não por um if. Um catch bem-intencionado nesse método reintroduziria o bug.

A ordem de registro vira a regra inteira

AddOpenBehavior monta a cebola do mais externo para o mais interno, na ordem em que você escreve: 

cfg.AddOpenBehavior(typeof(LoggingBehavior<,>));
cfg.AddOpenBehavior(typeof(ValidationBehavior<,>));
cfg.AddOpenBehavior(typeof(DespachoDeEventosBehavior<,>));   // ← ANTES
cfg.AddOpenBehavior(typeof(UnitOfWorkBehavior<,>));          // ← do que ele envolve
Logging
 └─ Validation
     └─ Despacho          ← drena DEPOIS que tudo lá dentro voltou
         └─ UnitOfWork    ← commita
             └─ Handler   ← enfileira

Trocar essas duas linhas de lugar reintroduz o bug sem nenhum sinal: compila, sobe, os testes de rota passam. Por isso a fatia deixa um teste que trava a ordem — comando que estoura no commit não pode produzir evento.

5. Send vs Publish: a outra metade do MediatR

Até agora só usamos metade da biblioteca. Vale a tabela:

IRequest (Command/Query)INotification (evento)
Como disparamediator.Send(...)publisher.Publish(...)
Quantos handlersExatamente 1 (zero ou dois = erro)0, 1 ou N — todos rodam
DevolveA resposta do handlerNada (Task)
Tempo verbalImperativo: CriarComentarioCommandPassado: ComentarioCriado

O tempo verbal não é preciosismo. Um comando pode ser recusado; um evento já aconteceu, e quem escuta não tem direito de veto. É por isso que ele só nasce pós-commit. Notifications na wiki do MediatR.

Amanhã, "mandar e-mail pro autor do post" é um segundo INotificationHandler<ComentarioCriado> — nenhuma linha do handler de criação muda. É o ganho concreto do Publish sobre chamar o Hub direto.

6. O handler do evento mora no Web — e o MediatR não o acha

IHubContext é ASP.NET Core; a Application não pode referenciá-lo (Clean Architecture, mesma razão de IStorage na Fatia 14 e dos seams do Google na Fatia 10). Então o ComentarioCriadoHandler fica em Web/Realtime/. Só que o registro do MediatR escaneia a assembly da Application: 

cfg.RegisterServicesFromAssembly(assembly);   // assembly = PensaComigo.Application

O handler no Web simplesmente não é encontrado — e o sintoma é traiçoeiro: Publish com zero handlers não é erro (ao contrário do Send). Tudo passa, nada chega na tela. Conserto de uma linha no Program.cs: 

builder.Services.AddScoped<INotificationHandler<ComentarioCriado>, ComentarioCriadoHandler>();

Escanear a assembly do Web também resolveria, mas puxaria todo controller e classe do host para dentro do scan por causa de um handler. Uma linha explícita é menos mágica e menos superfície.

7. Duas armadilhas de borda

CORS: o handshake manda header que a política não permite

Nossa política atual é .WithHeaders("Content-Type") — uma allowlist. O cliente JS do SignalR manda x-signalr-user-agent no POST /negotiate, e o preflight morre com um erro de CORS que não menciona SignalR em lugar nenhum. Os headers entram na lista.

Reconexão não recoloca a conexão nos grupos

withAutomaticReconnect() devolve a conexão, não a participação nos grupos: o grupo vive por ConnectionId, e o reconnect gera um novo. O front tem que reinvocar Entrar no onreconnected — e refazer o GET, porque o que aconteceu enquanto estava offline não é reenviado.

Pós-commit in-process não é entrega garantida. Se o processo morrer entre o CommitAsync e o Publish, o dado está no banco e o evento sumiu. Outbox transacional resolveria e é overkill aqui: a mitigação é o front tratar o stream como aceleração e o GET como verdade.
