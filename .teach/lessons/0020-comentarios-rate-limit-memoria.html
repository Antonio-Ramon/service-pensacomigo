Estado fora do banco: IMemoryCache, tempo de vida no DI e o relógio como parâmetro

Aula 20 · Fatia 20 · Ticket 07 — Comentários (moderação automática)

Vitória desta aula: qualquer leitor comenta sem conta em POST /api/v1/posts/{postId}/comentarios, pode responder um nível, palavrão é barrado antes de tocar no banco e o 6º comentário do mesmo visitante no mesmo minuto leva 429 — tudo isso sem nenhuma tabela nova.

1. Nem toda dependência é banco: IMemoryCache

Até aqui, todo estado do sistema morava no Postgres. O rate limit não precisa disso: são cinco carimbos de tempo que expiram em um minuto. Gravar isso em tabela seria pagar disco, migration e limpeza por um dado descartável. O .NET já traz o lugar certo: 

builder.Services.AddMemoryCache();          // no AddApplication()

public sealed class LimitadorDeComentarios(IMemoryCache cache)
{
    public void Registrar(string visitante)
    {
        var chave = $"comentarios:{visitante}";
        var carimbos = JanelaDeslizante.Registrar(
                           cache.Get<List<DateTime>>(chave) ?? [],
                           DateTime.UtcNow, Janela, Maximo)
                       ?? throw new MuitasRequisicoesException(...);

        cache.Set(chave, carimbos, Janela);   // expiração = a própria janela
    }
}

Repare no cache.Set(chave, valor, Janela): o terceiro argumento é expiração absoluta. Visitante que parou de comentar some do cache sozinho — não existe rotina de limpeza, não existe vazamento de memória crescendo por visitante. É o cache fazendo o trabalho que uma tabela exigiria código para fazer.

O teto desta escolha: IMemoryCache é memória do processo. Com duas instâncias da API atrás de um balanceador, cada uma conta seu próprio balde e o limite efetivo vira 10/min. Está marcado com ponytail: no código: o upgrade é IDistributedCache com Redis, e o resto do desenho não muda — porque a decisão ("estourou?") já está isolada numa função pura.

2. Tempo de vida no DI: por que Singleton, e não Scoped

Isto é específico de .NET e é a fonte silenciosa de bugs "funciona na minha máquina". Os três tempos de vida do contêiner:

Tempo de vidaUma instância por…Usado no projeto para
Transientcada injeçãoobjetos baratos e sem estado
Scopedrequisição HTTPDbContext, repositórios, handlers
Singletontoda a aplicaçãoLimitadorDeComentarios, IMemoryCache

O DbContext é Scoped de propósito: ele acumula o change tracker de uma requisição e precisa morrer no fim dela (aulas 4 e 18). Já o limitador é o oposto — se fosse Scoped, cada requisição nasceria com um balde vazio e o limite nunca bateria. O estado só serve se sobreviver entre requisições, logo: Singleton.

A regra que dói se você esquecer: um Singleton nunca pode receber um Scoped no construtor. Ele guardaria para sempre um DbContext da primeira requisição — objeto não thread-safe, compartilhado por todo mundo, com dados velhos. O contêiner do .NET até detecta isso na subida (captive dependency) quando o ValidateScopes está ligado, que é o padrão em Development. Por isso o limitador injeta IMemoryCache (que também é singleton) e nada mais.

3. O relógio como parâmetro: testar tempo sem esperar tempo

A conta do rate limit está numa função pura, com o "agora" entrando pela porta da frente: 

public static List<DateTime>? Registrar(
    IEnumerable<DateTime> carimbos, DateTime agora, TimeSpan janela, int maximo)
{
    var vigentes = carimbos.Where(c => agora - c < janela).ToList();

    if (vigentes.Count >= maximo) return null;   // null = estourou

    vigentes.Add(agora);
    return vigentes;
}

Se DateTime.UtcNow estivesse dentro desta função, provar que a janela de um minuto funciona exigiria um teste que dorme 61 segundos. Com o relógio como parâmetro, o teste apenas afirma que horas são: 

var anteriores = Enumerable.Repeat(Agora, 5).ToList();

Assert.Null(JanelaDeslizante.Registrar(anteriores, Agora.AddSeconds(59), Janela, 5));
Assert.NotNull(JanelaDeslizante.Registrar(anteriores, Agora.AddSeconds(61), Janela, 5));

É o mesmo movimento do GeradorSlug na aula 15 — impureim sandwich: o I/O e o relógio ficam nas bordas (a classe com o cache), a decisão fica no meio, pura e testável. Um detalhe de C# que vale registrar: o retorno é List<DateTime>? e o null é a resposta "estourou". O ?? no chamador transforma isso em exceção numa linha só.

Nota de .NET moderno: a partir do .NET 8 existe TimeProvider, a abstração oficial de relógio para injetar em classes que precisam de UtcNow ou de timer. Aqui não foi necessária, porque a única coisa que dependia do tempo virou parâmetro. Vale conhecer para quando a dependência não puder ser empurrada para a borda.

4. Onde cada regra mora: validator ou handler?

Esta fatia tem duas regras novas e elas foram para lugares diferentes. O critério não é gosto:

RegraOndePor quê
Palavrão no textoValidatordá para decidir só olhando o campo
Resposta de respostaHandlerprecisa ler o comentário pai no banco
// Validator: falha de formato do campo → 422 campo-a-campo
RuleFor(c => c.Conteudo)
    .Must(texto => !FiltroPalavrao.Contem(texto))
    .WithMessage("Revise seu comentário: ele contém termos não permitidos.");

// Handler: invariante de negócio → precisa do estado do banco
if (pai.ParentId is not null)
    throw new RegraDeNegocioException("Só é possível responder a um comentário original.");

Um AbstractValidator<T> vê só o command — nenhum repositório, nenhuma consulta. Se responder a pergunta exige ir ao banco, ela não cabe ali; é do handler. Guardar essa fronteira é o que impede o validator de virar um segundo handler.

E note onde a árvore de 1 nível é travada: no handler. O schema aceita parent_id apontando para qualquer comentário, em profundidade infinita — foi a Decisão #7 do projeto, deliberada. O banco garante integridade referencial; a política de produto fica no código, onde é barata de mudar.

5. A identidade do visitante anônimo é do servidor

public static string De(HttpContext ctx)
{
    var bruto = $"{ctx.Connection.RemoteIpAddress}|{ctx.Request.Headers.UserAgent}";

    return Convert.ToHexStringLower(SHA256.HashData(Encoding.UTF8.GetBytes(bruto)));
}

Mesma lição do path da imagem na aula 14, agora com outra roupa: o que identifica alguém não pode vir de quem está sendo identificado. Se o cliente mandasse o viewerHash no corpo, trocar de valor zeraria o limite — e na issue 08 (likes) permitiria curtir o mesmo post infinitas vezes. Como consequência disso, o controller monta o command com dados de duas origens que o corpo não controla: 

var command = new CriarComentarioCommand(
    postId,                          // da rota
    req.ParentId, req.Autor, req.Conteudo,
    HashVisitante.De(HttpContext));  // do servidor

O hash também serve à privacidade: o rate limit funciona igual, e nunca guardamos IP cru — que é dado pessoal.

6. Duas armadilhas que o código evita (e você vai reencontrar)

A resposta é montada antes do SaveChanges

comentarios.data_criacao tem default now() no banco. O handler devolve o ComentarioResponse e só depois o UnitOfWorkBehavior commita — ou seja, no momento em que a resposta é criada aquele campo ainda é default(DateTime), uma data no ano 1. Por isso ComentarioResponse simplesmente não tem DataCriacao; quem precisa da data é a listagem, que lê do banco.

Teste com estado global se contamina

private HttpClient ClienteVisitante()
{
    var client = factory.CreateClient();
    client.DefaultRequestHeaders.UserAgent.ParseAdd($"teste-{Guid.NewGuid():N}/1.0");
    return client;
}

No WebApplicationFactory não há IP nem User-Agent reais: todos os clientes gerariam o mesmo hash, dividiriam o mesmo balde, e o 6º comentário do arquivo inteiro tomaria 429 — quebrando um teste inocente lá no fim. Dar um User-Agent único a cada teste devolve o isolamento. Sempre que um teste depende de estado que vive fora dele, isole a chave desse estado.
