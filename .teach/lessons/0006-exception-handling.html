Uma exceção, um status HTTP

Aula 06 · Fatia 6 do Ticket 01 · IExceptionHandler, ProblemDetails e exceções tipadas

Vitória desta aula: entender como o handler lança uma exceção com significado de domínio (NaoEncontradoException) e um único ponto central traduz isso pro HTTP certo (404) — sem try/catch espalhado nem controller decidindo status.

1. O problema: onde vai o try/catch?

Todo caso de uso pode falhar: post não existe, regra violada, request inválido. A tentação é try/catch em cada controller decidindo o status. Isso espalha a mesma lógica e mistura HTTP com regra. A Clean Architecture quer o contrário:

  • A Application/Domain só sabe lançar a exceção certa — ela não conhece HTTP.
  • A Web tem um tradutor: exceção tipada → status code.

2. Exceções tipadas (moram no Domain)

Não é qualquer throw new Exception("..."). O tipo carrega o significado — é o que o tradutor vai casar depois: 

// Domain/Exceptions — o tipo É a informação
public sealed class NaoEncontradoException(string recurso, object chave)
    : Exception($"{recurso} '{chave}' não encontrado.");   // → 404

public sealed class RegraDeNegocioException(string mensagem) : Exception(mensagem);  // → 422

Um handler futuro faz só: throw new NaoEncontradoException("Post", id);. Ele não sabe nem se importa que isso vira 404.

3. O tradutor: IExceptionHandler (nativo do .NET)

Desde o .NET 8 não precisamos escrever middleware na mão. A plataforma já dá a interface IExceptionHandler. Implementamos uma classe: 

public sealed class GlobalExceptionHandler(IProblemDetailsService pd, ILogger<...> log)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        var (status, titulo) = ex switch          // o casamento por TIPO
        {
            NaoEncontradoException  => (404, "Recurso não encontrado"),
            ValidationException     => (422, "Validação falhou"),   // do FluentValidation
            RegraDeNegocioException => (422, "Regra de negócio violada"),
            _                       => (500, "Erro interno"),        // desconhecida = bug
        };
        ...
    }
}

O switch por padrão de tipo (pattern matching) é o coração: cada exceção conhecida vira um status; o _ pega o resto como 500 (e aí sim a gente loga — 500 é bug nosso, os outros são fluxo esperado).

4. ProblemDetails: o corpo do erro (RFC 7807)

Não devolvemos texto solto. O padrão da web é ProblemDetails — um JSON com forma fixa (status, title, detail). O ASP.NET já serializa pra você via IProblemDetailsService. Para validação, empilhamos os erros campo-a-campo numa extensão: 

problema.Extensions["erros"] = falhas.Errors
    .GroupBy(e => e.PropertyName)
    .ToDictionary(g => g.Key, g => g.Select(e => e.ErrorMessage).ToArray());
Repara na ligação com a Aula 05: o ValidationBehavior throw new ValidationException(falhas) lá no pipeline. Ele não devolve 422 — só lança. Quem traduz pra 422 é aqui. Pipeline lança, handler traduz.

5. Ligando no Program.cs (native, 3 linhas)

builder.Services.AddProblemDetails();                          // liga o serializador RFC 7807
builder.Services.AddExceptionHandler<GlobalExceptionHandler>(); // registra o tradutor
...
app.UseExceptionHandler();   // põe o middleware nativo no pipe (bem no topo)

UseExceptionHandler() sem argumento usa nosso IExceptionHandler registrado. Nenhuma classe de middleware escrita à mão — só configuração.

Por que não escrevemos "ExceptionHandlingMiddleware" (como o ticket dizia)? Porque o IExceptionHandler nativo faz o mesmo com menos código e já integra com ProblemDetails. Reutilizar a plataforma > reinventar middleware. O 429 (rate limit) ficou de fora: não há limitador ainda — entra quando existir.
