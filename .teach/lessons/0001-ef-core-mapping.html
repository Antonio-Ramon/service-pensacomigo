Como o C# vira tabela

Aula 01 · Fatia 1 do Ticket 01 · EF Core, DbContext e Fluent API

Vitória desta aula: entender como uma classe C# (Usuario, Post…) é traduzida numa tabela Postgres — e escrever essa tradução. No fim, a camada Persistence mapeia o schema inteiro e compila.

1. O modelo mental

Você vem de outra linguagem, então o atalho: EF Core é um ORM — Object-Relational Mapper. Ele é a ponte entre dois mundos:

Mundo dos objetos (C#)Mundo relacional (Postgres)
classe Usuariotabela usuarios
propriedade Emailcoluna email
instância na memórialinha (row)
propriedade de navegação Post.Autorforeign key autor_id

Três peças fazem isso funcionar:

  • DbContext — a sessão com o banco. Um objeto que representa "a conversa com o Postgres". Tem uma DbSet<T> por tabela e é ele que traduz LINQ → SQL e rastreia mudanças pra salvar.
  • Configuration (Fluent API) — a folha de tradução de cada entidade: qual tabela, qual chave, quais colunas, quais constraints, quais relacionamentos.
  • Migration — o diff entre o modelo atual e o banco, virado em SQL (vem na fatia 4).

2. Por que Fluent API e não atributos?

Existem duas formas de configurar: Data Annotations (atributos [Required] grudados na entidade) ou Fluent API (classes separadas). Escolhemos Fluent API porque a entidade do Domain não pode saber que existe banco de dados — é a regra da Clean Architecture (Domain não referencia Persistence). Toda config de persistência fica isolada no projeto Persistence. [docs EF Core]

3. Anatomia de uma Configuration

A folha de tradução do Usuario. Leia os comentários:

public class UsuarioConfiguration : IEntityTypeConfiguration<Usuario>
{
    public void Configure(EntityTypeBuilder<Usuario> builder)
    {
        builder.ToTable("usuarios");              // nome da tabela
        builder.HasKey(u => u.Id);                // primary key

        builder.Property(u => u.Nome)
               .HasColumnName("nome")
               .IsRequired();                     // NOT NULL

        builder.Property(u => u.Email)
               .HasColumnName("email")
               .IsRequired();
        builder.HasIndex(u => u.Email).IsUnique(); // UNIQUE

        builder.Property(u => u.IsAdmin)
               .HasColumnName("is_admin")
               .HasDefaultValue(false);           // DEFAULT false no banco
    }
}

Cada linha vira SQL na migration. u => u.Email é uma lambda — "aponte pra propriedade Email"; o EF lê a expressão pra saber de qual coluna você fala (não executa nada).

4. Relacionamentos — a parte que confunde

No banco, um relacionamento é uma foreign key. No C#, ele aparece como propriedades de navegação. Ex.: Post tem AutorId (a FK) e Autor (o objeto navegável). A config amarra os dois lados: 

builder.HasOne(p => p.Autor)          // um Post tem um Autor
       .WithMany(u => u.Posts)        // um Usuario tem muitos Posts
       .HasForeignKey(p => p.AutorId);

Casos que você vai ver nesta fatia:

  • 1:N — Post → Autor (acima).
  • Auto-referência — Comentario.Parent aponta pra outro Comentario (respostas de 1 nível).
  • N:N — Post ↔ Tag gera a tabela de junção post_tags. O EF cria ela sozinho a partir das duas navegações.
  • Unique composto — likes(post_id, viewer_hash) impede curtida duplicada.

5. O DbContext junta tudo

public class PensaComigoDbContext : DbContext
{
    public PensaComigoDbContext(DbContextOptions<PensaComigoDbContext> options)
        : base(options) { }

    public DbSet<Usuario> Usuarios => Set<Usuario>();
    public DbSet<Post> Posts => Set<Post>();
    // ...

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // varre o assembly e aplica TODA classe IEntityTypeConfiguration
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(PensaComigoDbContext).Assembly);
    }
}

ApplyConfigurationsFromAssembly é a linha preguiçosa boa: você nunca precisa registrar cada configuration à mão — some uma nova classe na pasta e ela entra sozinha.
