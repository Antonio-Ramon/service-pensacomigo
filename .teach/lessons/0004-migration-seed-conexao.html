Do modelo C# para tabelas reais no Postgres

Aula 04 · Fatia 4 do Ticket 01 · Migrations, seed com HasData e a conexão Supabase

Vitória desta aula: entender como o EF transforma suas classes + configs numa migration (script versionado), como plantar dados iniciais (HasData) e por que a conexão Supabase usa duas portas.

1. O que é uma migration

Você nunca escreve CREATE TABLE na mão. O EF compara dois estados: o snapshot do modelo anterior (arquivo ...ModelSnapshot.cs) com o modelo atual (entidades + configs). A diferença vira uma migration: 

dotnet ef migrations add InicialSchema \
  -p src/PensaComigo.Persistence \   onde a migration é gravada
  -s src/PensaComigo.Web             startup: de onde vem a connection string

Isso gera uma classe com Up() (aplica) e Down() (reverte). Nada toca o banco ainda — migrations add é offline, só lê seu código. Quem escreve no Postgres é o passo seguinte: 

dotnet ef database update -p src/PensaComigo.Persistence -s src/PensaComigo.Web

2. De onde o EF acha o DbContext (design-time)

Repara no -s Web: em design time o EF sobe o Program.cs, lê a DI e pega o PensaComigoDbContext registrado lá. Por isso a Fatia 4 finalmente registra o contexto no container — o que faltava desde a Fatia 3: 

// Persistence/DependencyInjection.cs — agora recebe IConfiguration
services.AddDbContext<PensaComigoDbContext>(opt =>
    opt.UseNpgsql(config.GetConnectionString("Default")));

Sem esse registro, dotnet ef reclamaria "No DbContext was found". AddDbContext já registra o contexto como Scoped (um por request) — o mesmo tempo de vida dos repositórios que dependem dele.

3. Seed idempotente com HasData

Os autores Antonio e Jéssica não são "dados de teste" — são parte do schema. Usamos HasData na configuration, então o seed entra na própria migration (vira INSERT no Up()) e roda uma vez só, sem duplicar: 

builder.HasData(
    new Usuario { Id = /* Guid FIXO */, Nome = "Antonio", ... });
HasData exige chave primária fixa (um Guid literal, não Guid.NewGuid()) — senão toda migration acharia que o registro "mudou". E toda coluna obrigatória precisa de valor explícito, inclusive DataCriacao: o now() default do banco não vale para linhas semeadas.

4. A conexão Supabase: uma porta só (nesta escala)

O Supabase oferece duas portas — 5432 direta e 6543 pooled (Supavisor). A pooled existe para tráfego alto: centenas de conexões curtas simultâneas (serverless). Este projeto tem 2 autores e tráfego baixo, então usamos a direta 5432 para tudo — migration e runtime. Uma connection string só.

Por que não a pooled para migration: o pooler em transaction mode quebra prepared statements e comandos de sessão que o EF usa no DDL. Ficando na direta, esse problema nem aparece. Só se o tráfego crescer você migra para 6543 — e aí ajusta o Npgsql (desligar prepared statements). Enquanto for direta, ignora.

SSL Mode=Require sempre — Supabase recusa texto puro. A string vai no user-secrets (fica na sua máquina, fora do git), que sobrepõe o appsettings.json em Development. Segredo real nunca é commitado.
