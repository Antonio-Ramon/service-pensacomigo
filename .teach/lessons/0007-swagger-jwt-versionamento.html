Aula 07 · Fatia 7 do Ticket 01 · JwtBearer, Swagger com Authorize e versionamento de rota

Vitória desta aula: entender como o backend valida o JWT que ele mesmo emitiu (não o do Google), o que cada Validate* protege, e por que a ordem UseAuthentication → UseAuthorization não pode inverter.

1. Dois tokens diferentes (não confunda)

No Pensa Comigo há dois JWTs no fluxo — e esta fatia só cuida do segundo:

  • Token do Google: o frontend faz o OAuth, recebe esse token e manda pro backend uma vez, no login. Validá-lo é papel da Fatia 02.
  • JWT próprio: depois de reconhecer o usuário, o backend emite o seu próprio JWT, assinado com uma chave secreta nossa. Toda requisição seguinte manda esse. É esse que configuramos aqui pra validar.

Por isso a chave é simétrica (SymmetricSecurityKey): quem assina e quem valida é a mesma parte — nós. Segredo único, via user-secrets (nunca no git).

2. Configurar a validação (e o que cada linha protege)

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options => options.TokenValidationParameters = new()
    {
        ValidateIssuer           = true,   // quem emitiu? tem que ser "pensacomigo"
        ValidateAudience         = true,   // pra quem? tem que ser nossa API
        ValidateLifetime         = true,   // expirou? recusa token vencido
        ValidateIssuerSigningKey = true,   // assinatura bate com NOSSA chave?
        ValidIssuer   = jwt["Issuer"],
        ValidAudience = jwt["Audience"],
        IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(jwt["Key"]!)),
    });
builder.Services.AddAuthorization();
Aqui não se é lazy: cada Validate* fecha uma porta. Desligar ValidateLifetime aceita token eterno; desligar ValidateIssuerSigningKey aceita token forjado por qualquer um. Segurança é a exceção à regra do "código mínimo".

3. Authentication vs Authorization (a ordem no pipe)

app.UseAuthentication();   // 1º: LÊ o token → descobre QUEM é (preenche User)
app.UseAuthorization();    // 2º: decide se ESSE quem PODE (checa [Authorize])
  • Authentication = identidade. Lê o Bearer, valida, monta o HttpContext.User.
  • Authorization = permissão. Olha o [Authorize] da rota contra esse User.

Inverter é bug: autorizar antes de autenticar significa decidir permissão sobre um usuário ainda anônimo — toda rota protegida cairia como não-autorizada.

4. Swagger com botão "Authorize"

Swagger lê os endpoints e desenha a UI. Pra testar rota protegida, ele precisa saber mandar o Bearer. Declaramos o esquema uma vez: 

options.AddSecurityDefinition("Bearer", new OpenApiSecurityScheme {
    Type = SecuritySchemeType.Http, Scheme = "bearer", BearerFormat = "JWT", In = Header });

options.AddSecurityRequirement(_ => new OpenApiSecurityRequirement {
    [new OpenApiSecuritySchemeReference("Bearer")] = [] });

O definition descreve o esquema; o requirement diz "aplique a todos". Aparece o cadeado Authorize no topo do Swagger — cola o token e ele acompanha cada chamada.

Detalhe de versão: Swashbuckle 10 usa Microsoft.OpenApi 2.x — namespace virou Microsoft.OpenApi (sem .Models), referência agora é OpenApiSecuritySchemeReference, e AddSecurityRequirement recebe uma factory (_ => ...). Aprendizado real: bibliotecas mudam de forma entre versões.

5. Versionamento /api/v1 (por que NÃO instalamos lib)

O ticket pede /api/v1. A tentação é a lib Asp.Versioning. Mas só existe v1 e nem há controller ainda — instalar máquina de versão pra uma versão é peso morto. A escolha ponytail: quando o primeiro controller chegar, o prefixo é só uma rota: 

[ApiController]
[Route("api/v1/[controller]")]   // prefixo = convenção; lib entra SÓ quando v2 existir
public class PostsController : ControllerBase { ... }

Regra que se repete no curso: native/convenção primeiro; dependência só quando ela paga o próprio peso.
