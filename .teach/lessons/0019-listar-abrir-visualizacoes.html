Feed público: Gridify no que importa, rota por slug e incremento atômico

Aula 19 · Fatia 19 · Ticket 06 — Listar / abrir / visualizações

Vitória desta aula: o site tem home. GET /api/v1/posts devolve o feed paginado e filtrável, GET /api/v1/posts/{slug} abre a meditação com autor e tags — os dois anônimos — e abrir conta visualização sem perder contagem quando dois leitores chegam no mesmo instante.

1. [AllowAnonymous] fura o [Authorize] do controller

Na aula 18 o [Authorize] subiu para a classe inteira, porque tudo ali era escrita. Agora entram dois GET públicos no mesmo controller. Não é preciso desmontar nada: 

[ApiController]
[Authorize]                        // padrão do controller: exige token
public class PostsController(ISender mediator) : ControllerBase
{
    [AllowAnonymous]               // exceção, na ação
    [HttpGet]
    public async Task<ActionResult<Pagina<PostResumoResponse>>> Listar(...)

A regra do ASP.NET Core aqui é assimétrica, e vale decorar: [AllowAnonymous] na ação vence o [Authorize] da classe, mas o contrário não acontece — pôr [Authorize] numa ação de um controller [AllowAnonymous] não protege nada, porque o filtro de autorização vê o AllowAnonymous mais permissivo e desiste. Traduzindo para o dia a dia: o padrão seguro fica na classe, e as exceções públicas ficam nas ações. Nunca o inverso.

2. Duas rotas GET, um conflito que não aconteceu

[HttpGet]                 // /api/v1/posts
[HttpGet("{slug}")]       // /api/v1/posts/respirar-devagar
[HttpPut("{id:guid}")]    // /api/v1/posts/8f2c...  (verbo diferente)

{slug} e {id:guid} ocupam a mesma forma de URL. Não colidem por dois motivos: o verbo é diferente (GET vs PUT/DELETE) e, mesmo se fosse o mesmo, a constraint :guid torna aquela rota mais específica — o roteador prefere a rota com constraint quando o valor casa, e cai na genérica quando não casa. Se um dia existir GET {id:guid} ao lado de GET {slug}, continua funcionando; sem a constraint, aí sim seria ambiguidade em tempo de execução.

3. Um GET que escreve: por que ICommand

Abrir o post incrementa qtd_visualizacoes. Isso é um efeito colateral — e o critério que a Fatia 17 firmou é justamente esse, não "escreve no Postgres". Então: 

public record AbrirPostCommand(string Slug) : ICommand<PostDetalheResponse>;

Estranha o nome Command atrás de um HttpGet? É o ponto: verbo HTTP e marcador CQRS descrevem coisas diferentes. O verbo é contrato com o cliente (é cacheável? o browser pode repetir?); o marcador diz ao UnitOfWorkBehavior se ele commita no fim do pipeline. Um GET com efeito colateral é uma decisão de produto comum — todo site de conteúdo conta view no GET — e o pipeline precisa saber disso.

Consequência prática: esse GET não é idempotente, então nunca coloque cache HTTP agressivo nem retry automático em cima dele sem pensar — cada repetição vira uma view a mais.

4. ExecuteUpdateAsync: o incremento que não perde contagem

O caminho óbvio seria carregar o post rastreado e fazer post.QtdVisualizacoes++. Ele funciona com um leitor e mente com dois. Dois requests simultâneos leem 10, ambos calculam 11, ambos gravam 11: uma view sumiu. É o lost update clássico — o cálculo aconteceu na sua memória, com um valor que já estava velho quando chegou lá. 

public Task IncrementarVisualizacoesAsync(Guid id, CancellationToken ct = default) =>
    db.Posts.Where(p => p.Id == id)
            .ExecuteUpdateAsync(s => s.SetProperty(
                p => p.QtdVisualizacoes,
                p => p.QtdVisualizacoes + 1), ct);

Isso vira UPDATE posts SET qtd_visualizacoes = qtd_visualizacoes + 1 WHERE id = …. A soma acontece dentro do banco, sob o lock da linha: dois requests simultâneos viram 12, sempre. Repare no segundo SetProperty: ele recebe uma lambda sobre a entidade, não um valor — é isso que gera coluna = coluna + 1 em vez de coluna = 11.

Duas coisas específicas de ExecuteUpdate que vão te morder algum dia: ele não passa pelo change tracker (o objeto que você tem em memória continua com o valor antigo — por isso o handler devolve post.QtdVisualizacoes + 1) e ele executa na hora, não no SaveChanges. Aqui isso é indiferente; num handler onde o UPDATE precisasse ser atômico junto de outras gravações, seria preciso uma transação explícita.

5. Listar é outro shape, não o mesmo post menor

public record PostResumoResponse(Guid Id, string Titulo, string Slug, string ImagemCapa,
    int TempoLeitura, int QtdCurtidas, int QtdVisualizacoes, DateTime DataCriacao);

Sem Conteudo, sem autor, sem tags. Vinte posts por página arrastando o jsonb inteiro do corpo seria um payload de megabytes para desenhar cards. O detalhe, esse sim, carrega tudo — e é aí que entra Include(p => p.Autor).Include(p => p.Tags), com AsNoTracking() porque ninguém vai mutar aquilo (é leitura pura; contraste com o ObterParaEdicaoAsync da aula 18).

6. O mapper do Gridify, agora com coleção

private static readonly IGridifyMapper<Post> Mapper = new GridifyMapper<Post>()
    .AddMap("titulo", p => p.Titulo)
    .AddMap("autor",  p => p.Autor.Nome)
    .AddMap("tag",    p => p.Tags.Select(t => t.Slug))   // N:N → EXISTS
    .AddMap("dataCriacao", p => p.DataCriacao);

if (string.IsNullOrWhiteSpace(consulta.OrderBy)) consulta.OrderBy = "dataCriacao desc";

O mapa tag aponta para uma coleção: o Gridify entende e o EF traduz ?filter=tag=saude-mental num EXISTS sobre a junção — filtro por tema de graça, sem endpoint novo. E o mapper continua sendo uma whitelist: o que não está ali não é filtrável, por mais que o cliente peça. Sem isso, a querystring viraria uma superfície de ataque sobre colunas que você nunca quis expor.

O OrderBy padrão é dataCriacao desc — feed é cronológico invertido. Mas o motivo mais duro é o da aula 13: sem ORDER BY o Postgres não promete a mesma ordem duas vezes, e a página 2 pode repetir ou pular itens que a página 1 já mostrou.
