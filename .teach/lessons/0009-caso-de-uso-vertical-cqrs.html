Do HTTP ao banco: a fatia vertical

Aula 09 · Fatia 9 · Ticket 02 (Auth) · Command → Controller → Handler → Response

Vitória desta aula: ver o pipeline da Fatia 5 ganhar vida. Até agora os behaviors eram um trilho sem trem. Hoje passa o primeiro trem de verdade — o login — e você entende como um caso de uso vira Command + Handler + Controller, cada peça com uma responsabilidade.

1. O que é uma "fatia vertical"

Um caso de uso corta as 5 camadas de cima a baixo: entra HTTP no Web, a regra roda na Application, os dados vêm da Persistence. Login é a primeira fatia inteira. O caminho é sempre este: 

POST /api/v1/auth/login
   → AuthController        (Web) só recebe e delega
   → mediator.Send(cmd)    (MediatR) entra na cebola de behaviors
   → Logging → Validation → UnitOfWork
   → LoginGoogleCommandHandler   (Application) A REGRA
   → LoginResponse         volta pela cebola até o HTTP 200

2. As três peças novas

Command — a mensagem. Um record: só dados de entrada + o tipo da resposta.

public record LoginGoogleCommand(string IdToken) : ICommand<LoginResponse>;

É ICommand (não IQuery) porque o 1º login grava google_id e foto — logo precisa passar pelo UnitOfWorkBehavior e commitar. Escreveu? Command.

Handler — onde a regra mora. Um handler por command. Recebe colaboradores por DI:

public class LoginGoogleCommandHandler(
    IGoogleTokenValidator google,      valida o token
    IUsuarioRepository usuarios,        busca no banco
    IJwtTokenGenerator jwt)             emite o JWT próprio
    : IRequestHandler<LoginGoogleCommand, LoginResponse>
{
    public async Task<LoginResponse> Handle(LoginGoogleCommand cmd, CancellationToken ct)
    {
        var conta = await google.ValidarAsync(cmd.IdToken, ct);
        var usuario = await usuarios.ObterPorEmailAsync(conta.Email, ct)
            ?? throw new NaoEncontradoException("Usuário", conta.Email);  fora do seed → 404
        if (usuario.GoogleId is null) { usuario.GoogleId = conta.GoogleId; /* + foto */ }
        return new LoginResponse(jwt.Gerar(usuario), usuario.Nome, usuario.ImagemUrl);
    }
}

Controller — magro de propósito. Nenhuma regra, nenhum if:

[HttpPost("login")]
public async Task<ActionResult<LoginResponse>> Login(LoginGoogleCommand command, CancellationToken ct)
    => Ok(await mediator.Send(command, ct));

O ASP.NET desserializa o JSON do corpo direto no LoginGoogleCommand. O controller só empurra pro MediatR. Toda a lógica ficou testável sem HTTP nenhum.

3. O primeiro validator de verdade

A Fatia 5 montou o ValidationBehavior, mas não havia o que validar. Agora há: 

public class LoginGoogleCommandValidator : AbstractValidator<LoginGoogleCommand>
{
    public LoginGoogleCommandValidator() =>
        RuleFor(c => c.IdToken).NotEmpty().WithMessage("O token do Google é obrigatório.");
}

Você não registra nem chama isso em lugar nenhum. O AddValidatorsFromAssembly (Fatia 5) acha por reflexão, e o behavior o roda antes do handler. Token vazio → ValidationException → 422, sem tocar no banco. Veja Aula 05.

4. Por que Google e JWT são interfaces

O handler depende de IGoogleTokenValidator e IJwtTokenGenerator — só interfaces, sem implementação ainda. Isso é um seam (costura), e é deliberado:

  • Regra da Clean Architecture: a Application não pode conhecer a lib do Google. A interface fica na Application; a implementação vai pra fora (Fatia 10).
  • Testabilidade: no teste de integração você troca o Google por um fake que devolve um email fixo — impossível bater no Google real num teste.
Por isso o endpoint ainda não roda de ponta a ponta: falta registrar as duas implementações na DI. Isso é a Fatia 10 (validar token Google de verdade + emitir o JWT com a chave simétrica que o Program.cs já valida desde a Fatia 7). Build verde, fluxo montado, regra testável — o trilho está pronto pro trem completo.
