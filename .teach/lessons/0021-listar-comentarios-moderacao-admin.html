Árvore rasa com filtered include e autorização por claim

Aula 21 · Fatia 21 · Ticket 07 — Comentários (leitura + moderação)

Vitória desta aula: a conversa do post é lida por qualquer um em GET /api/v1/posts/{postId}/comentarios — raízes paginadas, cada uma com suas respostas — e só quem tem is_admin=true no token consegue esconder ou apagar um comentário. Não-admin com token válido leva 403, não 401.

1. Paginar uma árvore: pagine as raízes, não as linhas

A tabela comentarios é plana: raiz e resposta são a mesma linha, separadas por parent_id. Se você paginar a tabela, pageSize=20 devolve 20 linhas — e a página pode terminar no meio de uma conversa, com uma resposta órfã cujo pai ficou na página seguinte. O usuário lê "Que bom que ajudou" sem ver a que.

A consulta pagina só as raízes, e cada raiz traz as respostas junto: 

var raizes = db.Comentarios.AsNoTracking()
    .Where(c => c.PostId == postId && c.Aprovado && c.ParentId == null)
    .Include(c => c.Respostas.Where(r => r.Aprovado).OrderBy(r => r.DataCriacao));

var (total, query) = await raizes.GridifyQueryableAsync(consulta, Mapper, ct);

Aquele Where dentro do Include é filtered include (EF Core 5+). Sem ele você teria três opções piores: carregar todas as respostas e filtrar em memória (traz lixo do banco), fazer um SELECT por raiz (N+1), ou escrever SQL na mão. O EF traduz isso para um JOIN com a condição embutida. Docs do filtered include.

TotalItems passa a significar "quantas conversas", não "quantas linhas" — e é isso que o front precisa para montar o paginador.

2. O mapper do Gridify é a fronteira de segurança

Desde a Fatia 13 o GridifyMapper é uma whitelist do que o cliente pode filtrar. Aqui ele vira controle de acesso, e é o detalhe mais fácil de errar da fatia: 

private static readonly IGridifyMapper<Comentario> Mapper = new GridifyMapper<Comentario>()
    .AddMap("autor", c => c.Autor)
    .AddMap("dataCriacao", c => c.DataCriacao);
    // aprovado, postId e parentId NÃO entram aqui

Se aprovado estivesse mapeado, ?filter=aprovado=false transformaria o endpoint público num painel de tudo que a moderação escondeu. O recorte fixo do endpoint (postId, aprovado, parentId == null) mora no Where do repositório, onde o cliente não alcança; a querystring só escolhe página, ordem e filtro dentro desse recorte.

Mesma ideia do postId: o controller faz query.PostId = postId depois do model binding. Mesmo que alguém mande ?postId=, a rota vence. É o padrão que você já viu no AutorId vindo da claim (Fatia 16) e no path da imagem montado no servidor (Fatia 14): dado que decide o que você enxerga nunca vem do cliente.

3. [Authorize] ≠ autorização

Até agora [Authorize] respondia uma pergunta só: "tem token válido?". Moderar exige a segunda pergunta: "quem é você?". O JWT já carrega a resposta desde a Fatia 10 — a claim is_admin. Falta ligá-la a uma regra nomeada, a policy: 

// Program.cs
builder.Services.AddAuthorization(opcoes =>
    opcoes.AddPolicy("Admin", politica => politica.RequireClaim("is_admin", "true")));

// ComentariosController.cs
[Authorize(Policy = "Admin")]
[HttpPatch("{id:guid}/ocultar")]

A regra fica em um lugar; os endpoints só citam o nome. Quando amanhã "admin" virar "admin ou moderador", você muda a policy e não caça atributos pelo projeto.

E repare no detalhe que quebra silenciosamente: RequireClaim compara string exata, e bool.ToString() em C# produz "True" com T maiúsculo. Por isso o gerador de token passou a emitir usuario.IsAdmin ? "true" : "false". Um T a mais e todo admin tomaria 403, sem nenhum erro no log.

401 vs 403 — a distinção que o ASP.NET faz sozinho:
401 Unauthorized = não sei quem você é (sem token, ou token inválido/expirado).
403 Forbidden = sei quem você é, e você não pode. A policy falhou.
Você não escreve nenhum if para isso: o middleware de autorização decide qual dos dois com base em ter havido autenticação bem-sucedida ou não.

4. Esconder ≠ apagar

Duas ações, dois efeitos diferentes — e a diferença é de negócio, não técnica: 

// Ocultar: a entidade vem RASTREADA do repo, então mudar a propriedade basta.
// O UPDATE sai no SaveChanges do UnitOfWorkBehavior (Fatia 5).
comentario.Aprovado = false;

// Deletar: some do banco. As respostas caem por OnDelete(Cascade) no parent_id.
comentarios.Remover(comentario);

Ocultar preserva o texto para auditoria e é reversível; deletar é definitivo. E note o que não foi preciso escrever: ao esconder uma raiz, as respostas dela não precisam ser escondidas uma a uma — a listagem só devolve respostas de raízes visíveis, então a conversa some inteira de graça. Quando a modelagem da leitura está certa, a escrita fica pequena.
