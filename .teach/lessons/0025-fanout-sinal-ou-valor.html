Sinal ou valor, grupo ou todos

Aula 25 · Fatia 25 · Curtida, visualização e feed ao vivo — estende o ADR 0001

Vitória desta aula: o realtime deixa de ser "coisa de comentário". Curtida e visualização sobem sozinhas na tela de quem está lendo, e post publicado aparece no feed de quem está na home. Três casos, um conceito novo: quem decide o formato do push é a pergunta "o cliente consegue redescobrir isso sozinho?".

1. A régua: sinal ou valor

A Aula 24 fechou com uma regra que parecia universal: o push é sinal, o GET é a verdade. Ela não é universal — é uma consequência, e vale enquanto duas coisas forem verdade:

PerguntaSim → sinalNão → valor
Refazer o GET é barato e sem efeito colateral?comentário, feeddetalhe do post
O payload mentiria se fosse aplicado direto?comentário (falta data, foto, respostas)um int não mente
O detalhe que quebra a regra: o GET do post é o AbrirPostCommand, e ele incrementa visualização. Um front que refizesse o GET a cada curtida inflaria o outro contador — o realtime de um número corrompendo o outro. Por isso CurtidasAtualizadas e PostVisualizado carregam o valor, e são os únicos que carregam.

Repare que a régua não fala de "tempo real"; fala de quem é dono da verdade. É a mesma pergunta da Fatia 19, quando o AbrirPostCommand passou a devolver QtdVisualizacoes + 1 em vez de reler do banco.

2. ExecuteUpdate não devolve valor. RETURNING devolve.

Para empurrar o número certo, alguém precisa saber o número. O contador é somado no banco, de forma atômica, justamente para o C# nunca precisar lê-lo antes: 

// Fatia 22 — atômico, mas devolve LINHAS AFETADAS, não o valor
db.Posts.Where(p => p.Id == id && p.QtdCurtidas + delta >= 0)
        .ExecuteUpdateAsync(s => s.SetProperty(p => p.QtdCurtidas, p => p.QtdCurtidas + delta), ct);

Ler depois com um SELECT seria uma segunda ida ao banco e uma corrida: entre o UPDATE e o SELECT cabe outro curtidor. O Postgres resolve os dois de uma vez com RETURNING: 

var atualizado = await db.Database.SqlQuery<int>(
    $"""
    UPDATE posts SET qtd_curtidas = qtd_curtidas + {delta}
    WHERE id = {id} AND qtd_curtidas + {delta} >= 0
    RETURNING qtd_curtidas
    """).ToListAsync(ct);

return atualizado.Count > 0 ? atualizado[0] : null;   // null = nenhuma linha casou
Interpolação aqui não é concatenação. SqlQuery recebe uma FormattableString: cada {delta} vira $1, $2… no comando enviado ao Postgres. O EF não tem como transformar isso em injeção — e é por isso que o mesmo código escrito com string comum nem compila.

E o null virou informação útil: nenhuma linha casou significa o contador não mudou (post inexistente, ou a guarda do não-negativo barrou o descurtir a mais). Anunciar mesmo assim empurraria um número velho para todo mundo no grupo — daí o if no handler, travado por teste que foi verificado falhando.

3. Grupo é para quem abriu alguma coisa

Curtida e visualização são do post: vão para Clients.Group(post:{id}), como o comentário. Post publicado não — quem está no feed não abriu post nenhum, e portanto não está em grupo algum. Esses vão para Clients.All. 

hub.Clients.Group(TempoRealHub.Grupo(evento.PostId)).SendAsync("CurtidasAtualizadas", evento.Qtd, ct);
hub.Clients.All.SendAsync("PostPublicado", evento.Slug, ct);

Com cinco eventos, o hub deixou de ser "o hub dos comentários" e virou o hub da aplicação: ComentariosHub → TempoRealHub, rota /hubs/tempo-real. Um hub por assunto seria pior, não melhor — cada hub é uma conexão WebSocket por aba.

4. Uma conexão por aba, do lado do front

Aqui o mesmo argumento cobra a fatura: a página do post tem três componentes ouvindo (comentários, curtidas, visualizações). Com o desenho da Aula 24 — conexão dentro do useEffect — seriam três WebSockets para receber eventos do mesmo grupo. A conexão subiu para um módulo (src/lib/tempoReal.ts) e passou a ser uma só; o que entra e sai com o componente agora é ouvinte e grupo, não conexão. 

useEffect(() => ouvirPost(postId, { CurtidasAtualizadas: setTotal }), [postId]);
De brinde, sumiu o “connection was stopped during negotiation”: não existe mais stop() para chegar no meio do negotiate. A conexão vive enquanto a aba viver. Em compensação, o onreconnected agora precisa reentrar em todos os grupos ativos — o módulo guarda esse conjunto, porque nenhum componente sozinho sabe dele.

5. Feed: quem redesenha é o servidor

A home é um server component. Em vez de duplicar a listagem no cliente só para conseguir atualizá-la, o ouvinte chama router.refresh() e o Next refaz o render no servidor com dados novos — sem F5 e sem segunda fonte de verdade. 

useEffect(() => ouvirGeral({
  PostPublicado: () => router.refresh(),
  PostRemovido: () => router.refresh(),
}), [router]);
E por isso o <FeedAoVivo /> NÃO entra no layout público, só nas três páginas de feed. Montado no layout, ele também rodaria na página do post — e lá um router.refresh() refaz o abrirPost, que incrementa visualização. A mesma armadilha da seção 1, entrando pela porta dos fundos.

6. O que ficou de fora, de propósito

  • Agendado que vence não emite nada. O post entra no ar porque DataPublicacao <= UtcNow passa a ser verdade — ninguém executa comando nenhum, e evento nasce de caso de uso. Realtime para isso exigiria um job, que o projeto não tem.
  • Quem está lendo um post deletado não é avisado. O evento chega (Clients.All), mas a página não faz nada com ele. Dá 404 no próximo clique.
  • Visualização empurra uma mensagem por leitor que abre. Para o volume deste blog é ruído nenhum; em post viral vira metralhadora. Teto anotado com ponytail:, upgrade é agregar num PeriodicTimer.

7. Checkpoint

1. Por que a curtida empurra o número, e o comentário só avisa?

2. Por que trocar ExecuteUpdateAsync por RETURNING?

3. Por que PostPublicado vai em Clients.All?

4. Por que a conexão saiu do useEffect e virou módulo?

5. Por que o <FeedAoVivo /> não fica no layout público?
