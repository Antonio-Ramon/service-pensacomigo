Uma feature inteira: criar e listar Tags

Aula 12 · Fatia 12 · Ticket 03 (Tags) · Command + Query · [Authorize] vs [AllowAnonymous] · campo calculado

Vitória desta aula: a primeira feature não-auth completa. Um endpoint público GET /api/v1/tags (qualquer um lista) e um protegido POST /api/v1/tags (só autor logado cria) — no mesmo controller. Você junta tudo que já aprendeu: Command (Aula 09), Query (Aula 11), validator, repositório.

1. Uma feature = uma pasta, dois lados do CQRS

Até agora Command e Query moraram em features separadas (Login, Perfil). Tags é a primeira que tem os dois lados. A organização segue o caso de uso, não a camada técnica: 

Application/Tags/
├── TagResponse.cs           shape de saída, compartilhado
├── Criar/                   lado ESCRITA
│   ├── CriarTagCommand.cs        : ICommand<TagResponse>
│   ├── CriarTagCommandValidator.cs
│   └── CriarTagCommandHandler.cs
└── Listar/                  lado LEITURA
    ├── ListarTagsQuery.cs        : GridifyQuery, IQuery<Pagina<TagResponse>>
    └── ListarTagsQueryHandler.cs

Mesma máquina do MediatR pros dois; o marcador (ICommand vs IQuery) decide se o UnitOfWorkBehavior commita. Criar grava → commita. Listar só lê → não.

2. Um controller, duas posturas de segurança

O atributo de autorização mora por action. No mesmo TagsController: 

[AllowAnonymous]           público: sem token, todo mundo lista
[HttpGet]
public ... Listar([FromQuery] ListarTagsQuery query, ...) => Ok(await mediator.Send(query, ct));

[Authorize]                protegido: sem token = 401 automático
[HttpPost]
public ... Criar(CriarTagCommand command, ...) => Ok(await mediator.Send(command, ct));

"Autor cria tag (autenticado)" do ticket vira uma linha: [Authorize]. Repare que CriarTagCommand não tem campo autorId. A tag não guarda autor — a regra é só "estar logado". Se guardasse, o id viria da claim (Aula 11), nunca do body: cliente não decide quem é o autor.

3. Slug: campo calculado vive no handler

Convenção do projeto (igual TempoLeitura): o que é derivado se calcula na Application, não na entidade. O cliente manda só Nome; o handler produz o Slug — a versão URL-friendly: 

"Saúde Mental"  →  GerarSlug()  →  "saude-mental"

Tirar acento em C# tem um truque idiomático: Normalize(FormD) separa a letra do acento (á → a + ´), e aí você joga fora as marcas (NonSpacingMark). Depois um regex troca o resto por hífen: 

var d = nome.Trim().ToLowerInvariant().Normalize(NormalizationForm.FormD);
// ...descarta os NonSpacingMark, sobra "saude mental"...
return Regex.Replace(semAcento, "[^a-z0-9]+", "-").Trim('-');

4. Regra de negócio: 422 amigável > 500 do banco

O slug tem índice único no Postgres (TagConfiguration). Se dois nomes colidem, o banco rejeitaria — mas o erro cru vira um 500 feio. Melhor checar antes e devolver a exceção tipada da Aula 06: 

if (await tags.ExistePorSlugAsync(slug, ct))
    throw new RegraDeNegocioException($"Já existe uma tag equivalente a \"{cmd.Nome}\".");

O GlobalExceptionHandler traduz isso pra 422 com mensagem clara. O índice único continua lá como rede de segurança contra corrida — mas o caminho normal dá um erro que o frontend entende.

5. O teste de integração prova o contrato

O ticket pede exatamente três coisas — o teste as afirma em cima do Postgres real: 

POST sem token            → 401                       criar exige JWT
POST com token do seed    → 200 + slug "saude-mental"  autor cria
GET  anônimo              → a página contém a tag       público
Atualizado depois: a listagem foi conformada ao padrão Gridify (decisão project-wide, arquitetura §7.1) — ListarTagsQuery herda GridifyQuery e a resposta virou o envelope { items, totalItems } em vez de lista crua. Ver Aula 13.

Detalhe elegante: pra ter um JWT válido no teste, ele reusa o próprio IJwtTokenGenerator da API (resolvido da DI) e o usuário do seed. Nada de forjar token na mão — a mesma peça que assina em produção assina no teste.
