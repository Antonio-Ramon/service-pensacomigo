Quem está batendo na porta? Lendo o token no endpoint

Aula 11 · Fatia 11 · Ticket 02 (Auth) · [Authorize] + ClaimsPrincipal + 1º Query CQRS

Vitória desta aula: o GET /api/v1/usuarios/me devolve o perfil do usuário logado. Sem token → 401 automático. Com token → a API sabe QUEM você é lendo as claims que o login assinou na Aula 10. E de brinde: seu primeiro Query — o lado leitura do CQRS.

1. [Authorize]: o porteiro

Um atributo em cima da action. O middleware UseAuthentication (Fatia 7) já tentou validar o Bearer token em toda requisição; o [Authorize] só decide: tem token válido? passa. Não tem? 401 antes do seu código rodar. Você não escreve nenhum if — o pipeline faz. 

[Authorize]
[HttpGet("me")]
public async Task<ActionResult<PerfilResponse>> EuMesmo(CancellationToken ct)

2. User: quem o token diz que você é

Dentro de qualquer controller existe User — um ClaimsPrincipal que o middleware montou a partir das claims do JWT. Claims são as afirmações assinadas que você escreveu no JwtTokenGenerator: sub (o id), email, is_admin. Ler é buscar pela chave: 

var id = Guid.Parse(User.FindFirstValue(JwtRegisteredClaimNames.Sub)!);

O ! afirma "não é null" — o [Authorize] já garantiu que há um token, e todo token nosso carrega o sub.

⚠️ O pega-ratão das claims. Por padrão o handler JWT renomeia claims na entrada: sub vira ...nameidentifier, email vira uma URL gigante. Herança dos velhos tempos do SAML. Então FindFirstValue("sub") voltaria null! Desligamos isso no Program.cs com uma linha pra os nomes chegarem intactos: 
options.MapInboundClaims = false; // sub continua sub

3. Primeiro Query: o lado leitura do CQRS

Na Aula 09 você fez um Command (muda estado, commita). Agora o oposto: um Query — só lê. Mesma máquina do MediatR, marcador diferente: 

public record ObterPerfilQuery(Guid UsuarioId) : IQuery<PerfilResponse>;

Por que separar Command de Query? Intenção explícita: o UnitOfWorkBehavior (Fatia 5) só dá SaveChanges pra IBaseCommand — um Query nunca grava sem querer. O tipo comunica "isto é leitura pura", e o pipeline respeita.

4. O trem inteiro

GET /usuarios/me  →  [Authorize] valida o JWT           sem token = 401
                  →  controller lê `sub` do User         o id do dono do token
                  →  Send(ObterPerfilQuery(id))          MediatR acha o handler
                  →  handler busca no repo (dados frescos)nome/foto não cabem no token
                  →  PerfilResponse                       200 OK

Repare: o token prova quem (barato, offline), mas nome e foto vêm do banco (frescos). Se a pessoa trocou a foto, o /me reflete — o token não precisa ser reemitido.
