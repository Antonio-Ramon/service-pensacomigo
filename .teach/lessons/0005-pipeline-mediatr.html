A cebola de behaviors do MediatR

Aula 05 · Fatia 5 do Ticket 01 · Pipeline behaviors, CQRS e Unit of Work

Vitória desta aula: entender como log, validação e commit saem de dentro de cada handler e viram middleware de mensagem — e por que a ordem dos behaviors e o marcador ICommand decidem tudo.

1. Request → Handler, e o que embrulha isso

No MediatR, cada caso de uso é uma mensagem (IRequest<T>) tratada por um único Handler. Um behavior (IPipelineBehavior) é um middleware que embrulha esse handler — idêntico ao middleware HTTP, mas para mensagens. Todo request atravessa uma cebola de behaviors, e a resposta volta pela mesma cebola: 

Request → Logging → Validation → UnitOfWork → HANDLER
                                             ↓
Response ← Logging ← Validation ← UnitOfWork ←┘

Cada behavior recebe um next. Chamou next() → continua pra dentro. Não chamou (ex.: validação falhou) → corta o fluxo ali. É isso que tira código transversal de dentro de cada handler.

2. A assinatura de um behavior

public class LoggingBehavior<TRequest, TResponse>(ILogger<...> logger)
    : IPipelineBehavior<TRequest, TResponse> where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        logger.LogInformation("Tratando {Request}", typeof(TRequest).Name);
        var resposta = await next(ct);   // chama o próximo elo (ou o handler)
        logger.LogInformation("Tratado {Request}", typeof(TRequest).Name);
        return resposta;
    }
}

É genérico aberto (<,>): um mesmo behavior serve para toda mensagem do sistema. Registramos com AddOpenBehavior(typeof(LoggingBehavior<,>)).

3. Por que a ordem importa

A ordem de registro é a ordem de execução (mais externo primeiro): 

cfg.AddOpenBehavior(typeof(LoggingBehavior<,>));      // mais externo
cfg.AddOpenBehavior(typeof(ValidationBehavior<,>));
cfg.AddOpenBehavior(typeof(UnitOfWorkBehavior<,>));   // mais interno, colado no handler
  • Logging por fora → registra tudo, até o que morre na validação.
  • Validation no meio → se o request é inválido, throw antes de tocar no banco.
  • UnitOfWork por dentro → só commita depois que o handler rodou com sucesso.

4. CQRS: por que o UnitOfWork precisa saber Command vs Query

CQRS = separar Command (escreve) de Query (lê). Dar SaveChanges numa leitura é puro desperdício. Então o UnitOfWorkBehavior só commita em Commands. Como ele distingue? Um marcador: 

public interface IBaseCommand;                                 // só para o teste `is`
public interface ICommand<out T> : IRequest<T>, IBaseCommand;   // escrita
public interface IQuery<out T>   : IRequest<T>;                  // leitura
if (request is not IBaseCommand)
    return await next(ct);          // Query: passa sem commit

var resposta = await next(ct);
await uow.CommitAsync(ct);          // Command: commita ao fim
return resposta;

5. A ponte Unit of Work (a regra da Clean Architecture)

O behavior mora na Application, que só conhece o Domain — nunca o EF. Mas quem salva é o DbContext (Persistence). A ponte é uma interface no Domain: 

// Domain — a abstração
public interface IUnitOfWork { Task<int> CommitAsync(CancellationToken ct = default); }

// Persistence — o DbContext JÁ é a unidade de trabalho
public class PensaComigoDbContext : DbContext, IUnitOfWork
{
    public Task<int> CommitAsync(CancellationToken ct = default) => SaveChangesAsync(ct);
}
Na DI, registramos IUnitOfWork apontando para a mesma instância Scoped do DbContext: AddScoped<IUnitOfWork>(sp => sp.GetRequiredService<PensaComigoDbContext>()). Se registrasse um new, os repositórios rastreariam mudanças num contexto e o commit sairia noutro — nada seria salvo.

Repara: os PostRepository etc. não chamam SaveChanges (o comentário "fica pro UnitOfWorkBehavior" da Fatia 3). Eles só rastreiam (AddAsync); o commit único e atômico acontece uma vez, no fim, pelo behavior.
