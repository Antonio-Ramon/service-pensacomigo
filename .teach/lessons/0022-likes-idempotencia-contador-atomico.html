Idempotência, unicidade no banco e contador atômico

Aula 22 · Fatia 22 · Ticket 08 — Likes anônimos

Vitória desta aula: qualquer leitor curte um post em POST /api/v1/posts/{postId}/curtidas e descurte com DELETE na mesma rota. Clicar cinco vezes deixa o contador em 1. Não porque o front bloqueia o botão — porque o banco não deixa a segunda linha existir.

1. Idempotência: a mesma requisição, o mesmo resultado

Uma operação é idempotente quando repeti-la não muda nada além da primeira vez. DELETE /curtidas de quem nunca curtiu não é erro — o estado final desejado ("este visitante não curte este post") já vale. Devolver 404 ali obrigaria o front a saber de antemão se curtiu, e a rede é imprevisível: o cliente pode ter recebido a resposta e perdido, e vai reenviar.

No nosso código isso aparece como dois return silenciosos: 

// curtir
if (await likes.ExisteAsync(cmd.PostId, cmd.Visitante, ct))
    return Unit.Value;          // já curtiu: 204, sem contar de novo

// descurtir
var like = await likes.ObterAsync(cmd.PostId, cmd.Visitante, ct);
if (like is null) return Unit.Value;   // não curtia: 204, nada a fazer

Note que os dois devolvem 204, o mesmo da chamada que fez efeito. O cliente não precisa distinguir; ele só quer saber que acabou naquele estado. Definição no MDN — por spec, PUT e DELETE são idempotentes, POST não é obrigado a ser. O nosso é, de propósito.

2. if não garante unicidade. Constraint garante.

Aquele ExisteAsync é check-then-act: você lê, decide, escreve. Entre o ler e o escrever cabe outra requisição inteira. Dois cliques simultâneos do mesmo visitante: 

req A: SELECT ... → não existe
req B: SELECT ... → não existe     ← A ainda não gravou
req A: INSERT like
req B: INSERT like                 ← duas linhas, contador em 2

Nenhum if em C# fecha essa janela, porque a janela existe entre duas idas ao banco. Quem fecha é o índice único que já estava no schema desde a Fatia 1: 

builder.HasIndex(l => new { l.PostId, l.ViewerHash }).IsUnique();

O segundo INSERT estoura DbUpdateException, que o GlobalExceptionHandler da Fatia 6 já traduz para 409. Ou seja: o if é conveniência (transforma o caso comum num 204 limpo), a constraint é garantia. Só a segunda é verdade sob concorrência.

Regra geral: toda vez que você escrever "primeiro eu verifico se já existe", pergunte quem impede que dois processos verifiquem ao mesmo tempo. Se a resposta não for "uma constraint" ou "um lock", você tem um bug raro — desses que só aparecem em produção, no dia de maior tráfego.

3. Contador desnormalizado: coluna = coluna + 1, nunca ler-somar-gravar

qtd_curtidas vive no post para a listagem não fazer um COUNT por card. Mantê-lo é o mesmo problema da Fatia 19, agora nos dois sentidos: 

public Task AjustarCurtidasAsync(Guid id, int delta, CancellationToken ct = default) =>
    db.Posts.Where(p => p.Id == id && p.QtdCurtidas + delta >= 0)
            .ExecuteUpdateAsync(s => s.SetProperty(p => p.QtdCurtidas, p => p.QtdCurtidas + delta), ct);

Se em vez disso você carregasse o post e fizesse post.QtdCurtidas++, dois visitantes simultâneos leriam 5, ambos gravariam 6, e uma curtida sumiria — lost update. Com ExecuteUpdateAsync quem soma é o Postgres, dentro de uma única instrução, sob o lock da linha. Docs do ExecuteUpdate.

O && p.QtdCurtidas + delta >= 0 no Where é o cinto de segurança: um descurtir a mais nunca deixa o contador negativo — a linha simplesmente não casa e o UPDATE afeta zero linhas. Guarda no banco, não if no C#.

4. O preço: ExecuteUpdate não entra no Unit of Work

Aqui está a parte que quase ninguém conta. ExecuteUpdateAsync vai ao banco na hora — não passa pelo change tracker, não espera o SaveChanges do UnitOfWorkBehavior. Então a fatia grava em duas transações: 

handler:   ExecuteUpdate  → UPDATE posts SET qtd_curtidas = qtd_curtidas + 1   (commit já)
behavior:  CommitAsync    → INSERT INTO likes ...                             (commit depois)

Se o INSERT falhar (a corrida do item 2), o incremento já foi. O contador fica um acima da realidade. Aceitamos isso conscientemente — está marcado com ponytail: no código, e o caminho de upgrade é uma transação explícita envolvendo o behavior inteiro.

A lição não é "ExecuteUpdate é ruim": é que toda otimização que pula uma camada perde as garantias daquela camada. Você pulou o change tracker para ganhar atomicidade por linha; perdeu a atomicidade do caso de uso. Saber qual das duas dói mais no seu domínio é a decisão — aqui, contador levemente adiantado dói menos que curtida perdida.

5. Quem é "o mesmo visitante"?

O viewer_hash da Fatia 20 volta, com uma promoção: lá ele era chave de um balde em memória, aqui é coluna com índice único. Mesmo cálculo, no servidor: 

HashVisitante.De(HttpContext)   // SHA-256 de IP + User-Agent

Se o cliente mandasse o hash, bastaria trocar um caractere para curtir de novo — o mesmo motivo pelo qual o path da imagem (Fatia 14) e o autor do post (Fatia 16) são montados no servidor. É aproximado por natureza: mesma rede corporativa e mesmo navegador colidem, VPN nova conta como visitante novo. Para um contador de curtidas de blog, aproximado basta.

Repare também no que não tem aqui: rate limit. Comentário precisou de um (LimitadorDeComentarios) porque um visitante pode escrever infinitos. Curtida já é limitada a uma por visitante por post — pela constraint. Modelagem certa dispensa mecanismo.
