N:N com o change tracker e o jsonb de verdade

Aula 16 · Fatia 16 · Ticket 05 — CriarPostCommand

Vitória desta aula: POST /api/v1/posts existe. Um comando só grava em três formas diferentes ao mesmo tempo: colunas normais, uma coluna jsonb (o array de blocos) e linhas numa tabela de junção (post_tags) que nenhuma entidade sua enxerga. E as duas funções puras da Fatia 15 finalmente entraram no handler.

1. O caso de uso inteiro em 4 passos

slug        = ResolverColisao(Gerar(titulo), slugs já ocupados no banco)   ← puro (Fatia 15)
tags        = repo.ObterPorIdsAsync(cmd.TagIds)                       ← I/O
tempo       = CalculadoraTempoLeitura.Calcular(cmd.Conteudo)          ← puro (Fatia 15)
posts.AdicionarAsync(new Post { … })                                  ← I/O

É o impureim sandwich da aula passada, agora com recheio real. Repare que nada aqui commita: o UnitOfWorkBehavior (Fatia 5) vê que o request é IBaseCommand e chama o SaveChanges depois que o handler retorna. É naquele único SaveChanges que os três formatos de escrita acontecem juntos, numa transação.

2. O ponto da aula: N:N é sobre identidade, não sobre dados

A tentação é montar as tags a partir do que chegou no JSON: 

// ERRADO — parece inofensivo e duplica o banco inteiro
Tags = cmd.TagIds.Select(id => new Tag { Id = id }).ToList()

O EF Core não olha para o Id e conclui "ah, essa já existe". Ele olha para o change tracker: toda entidade que ele não conhece entra como EntityState.Added. Resultado do SaveChanges: um INSERT INTO tags — que estoura o índice único do slug, ou pior, passa e duplica a tag.

Por isso o repositório carrega as tags, e de propósito sem AsNoTracking(): 

// TagRepository — o único método do repo que NÃO usa AsNoTracking
public Task<List<Tag>> ObterPorIdsAsync(IEnumerable<Guid> ids, CancellationToken ct = default) =>
    db.Tags.Where(t => ids.Contains(t.Id)).ToListAsync(ct);

Entidades vindas dessa consulta chegam ao tracker como Unchanged. Aí, ao pendurá-las em post.Tags, o EF conclui a única coisa que sobrou para concluir: a tag já existe, o post é novo, então o que mudou foi o vínculo — e emite só o INSERT INTO post_tags.

Regra de bolso: AsNoTracking() em tudo que é leitura pura (como o ListarAsync do Gridify, Fatia 13). Tracking quando a entidade lida vai participar de uma escrita. É a diferença entre consultar e relacionar.

E a tabela post_tags? Não tem classe, não tem DbSet. Ela existe só no PostConfiguration (Fatia 1), naquele UsingEntity("post_tags", …) — o EF chama isso de skip navigation: você navega Post.Tags e a junção fica invisível.

3. O jsonb parando de ser teoria

Na Fatia 2 você configurou HasConversion + ValueComparer para List<Bloco> e não tinha o que gravar. Agora tem. O que o EF faz no SaveChanges: 

C#:        List<Bloco> { Bloco{Tipo=Texto, Html="<p>…"}, Bloco{Tipo=Imagem, ImagemPath="…"} }
             ↓  HasConversion(JsonSerializer.Serialize)
Postgres:  coluna `conteudo` jsonb  →  [{"tipo":0,"ordem":1,"html":"<p>…"}, …]

Duas consequências que você precisa carregar daqui pra frente:

  • É um blob, não uma tabela. Não dá pra WHERE num campo de bloco via LINQ, não dá pra ordenar por ele, não tem FK. Por isso Tag é entidade (você navega, filtra e conta por ela) e Bloco é jsonb (você só lê e escreve inteiro).
  • Ordem é dado, não é o índice do array. O handler grava [.. cmd.Conteudo.OrderBy(b => b.Ordem)] — o campo Ordem é a verdade; a posição no array é só uma conveniência de leitura.
Sintaxe nova de C#: aquele [.. algo] é a collection expression com spread (C# 12). [.. lista.OrderBy(…)] é lista.OrderBy(…).ToList() com o tipo inferido do destino — o mesmo [] que você já viu inicializando public List<Bloco> Conteudo { get; set; } = [];.

4. Validar um modelo flat: RuleForEach + switch expression

Bloco é flat de propósito (CLAUDE.md): texto, imagem e link coexistem como campos nuláveis e o Tipo diz quais valem. O preço disso é que o compilador não garante nada — um bloco Tipo=Texto com Html=null compila liso. Quem cobra a coerência é o validator, na fronteira: 

RuleForEach(c => c.Conteudo).Must(Coerente)
    .WithMessage("Bloco incompleto: cada tipo exige o seu campo…");

private static bool Coerente(Bloco b) => b.Tipo switch
{
    TipoBloco.Texto  => !string.IsNullOrWhiteSpace(b.Html),
    TipoBloco.Imagem => !string.IsNullOrWhiteSpace(b.ImagemPath),
    TipoBloco.Link   => !string.IsNullOrWhiteSpace(b.LinkUrl),
    _ => false,
};

RuleForEach aplica a regra item a item e o erro sai com índice (Conteudo[2]), então o front sabe qual bloco pintar de vermelho. O switch aqui é expressão, não comando: cada braço é o valor de retorno, e o _ é o descarte obrigatório. O 422 sai sozinho — ValidationBehavior (Fatia 5) roda antes do handler e o GlobalExceptionHandler (Fatia 6) formata.

5. Request ≠ Command (de novo)

CriarPostRequest(Titulo, ImagemCapa, TagIds, Conteudo)          o que o cliente manda
CriarPostCommand(AutorId, Titulo, ImagemCapa, TagIds, Conteudo)  o que o handler recebe

Mesmo movimento da Fatia 14: o AutorId sai de User.FindFirstValue(JwtRegisteredClaimNames.Sub), nunca do corpo. Se viesse do JSON, qualquer autor autenticado publicaria assinando o nome de outro. Vale a regra: todo campo que responde "de quem é isso?" vem da claim.

6. Onde o erro amigável mora

tag inexistente no TagIds  →  NaoEncontradoException  →  404   Except() acha quais faltaram
bloco incoerente           →  ValidationException     →  422   antes do handler
sem token                  →  —                       →  401   [Authorize], sem código seu

O cmd.TagIds.Except(vinculadas.Select(t => t.Id)) é diferença de conjuntos do LINQ: o que foi pedido menos o que voltou do banco = o que não existe. Sem isso, um id inventado sumiria em silêncio e o post nasceria com menos tags do que o autor escolheu — o pior tipo de bug, o que não reclama.
