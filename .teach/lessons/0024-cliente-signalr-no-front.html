O cliente SignalR no front

Aula 24 · Fatia 24 · A outra metade do ADR 0001 — repo front-pensacomigo

Vitória desta aula: dois navegadores no mesmo post. Um comenta, o outro vê aparecer — sem F5, sem polling. O backend da Aula 23 já empurra; falta alguém do outro lado escutando.

1. Por que um pacote, se WebSocket é nativo do browser

new WebSocket("wss://…") existe sem instalar nada. Mas o endpoint do SignalR não é um WebSocket cru: antes vem um POST /hubs/tempo-real/negotiate que devolve o connectionId e a lista de transportes; depois um handshake de protocolo ({"protocol":"json","version":1}), e as mensagens são frames tipados terminados em \u001e. Falar isso na mão é o que a Aula 23 fez em Python de propósito, para provar que o servidor estava de pé — não é como se escreve um cliente.

@microsoft/signalr é o cliente oficial do mesmo protocolo: ele faz o negotiate, o handshake, o fallback para Server-Sent Events ou long polling quando a rede bloqueia WS, e a reconexão com backoff. É a única dependência nova da fatia. 

npm i @microsoft/signalr
Nota da Aula 25: o hub foi renomeado para TempoRealHub em /hubs/tempo-real quando passou a carregar curtida, visualização e feed — e a conexão saiu do useEffect para um módulo compartilhado. O raciocínio desta aula continua valendo; mudaram a rota e o lugar onde a conexão mora.

2. As três strings que o compilador não vigia

Este é o ponto que mais dói na prática. O TypeScript confere quase tudo neste front — os DTOs vêm de src/types/api.d.ts, gerado do OpenAPI. Mas a conversa com o Hub atravessa três strings que ninguém valida em tempo de compilação, e cujo erro é silencioso: nada estoura, simplesmente não chega mensagem.

StringOnde nasce no backendSintoma se errar
"/hubs/tempo-real"MapHub<TempoRealHub>(…) no Program.cs404 no /negotiate — este, pelo menos, aparece no Network
"Entrar"método public do TempoRealHuba conexão sobe, o grupo nunca é entrado, nada chega
"ComentarioCriado"1º argumento do SendAsync no handlero servidor empurra, o cliente ignora, nada chega
Em C# quem chama o Hub errado toma exceção; em JS o invoke de método inexistente rejeita a promise — e um .catch(() => {}) mal colocado engole. Ao depurar realtime, a primeira pergunta é sempre "as três strings batem?", e a segunda é "o /negotiate devolveu 200?".

3. O push é um sinal, não o dado

A tentação é mandar o comentário que chegou direto para dentro do useState. Olha o que o servidor empurra: 

public record ComentarioResponse(Guid Id, Guid PostId, Guid? ParentId,
                                 string Autor, string Conteudo, bool Aprovado);

E olha o que a lista na tela consome:

public record ComentarioListaResponse(Guid Id, string Autor, string Conteudo,
    DateTime DataCriacao, bool Aprovado, string? AutorImagemUrl, bool EhAutorDoPost,
    IReadOnlyList<RespostaResponse> Respostas);

Faltam DataCriacao (a coluna tem default now() — no momento em que o evento nasce o valor ainda não voltou do banco), AutorImagemUrl, EhAutorDoPost e Respostas. Dá para inventar os quatro no cliente; foi exatamente o que o formulário já faz no envio otimista, e é dívida barata ali porque quem escreveu sabe quem é. Para o comentário de outra pessoa, seria chute.

A regra que fecha o ADR: o stream é aceleração, o GET é a verdade. Chegou evento → refaz a listagem. Isso não é preguiça: como a Aula 23 mostrou, um processo que morre entre o commit e o publish grava o comentário e perde o evento. Um front que só sabe aplicar deltas fica permanentemente errado; um que refaz o GET se conserta sozinho na próxima mensagem — ou no próximo F5.

4. Ciclo de vida: o efeito abre, o cleanup fecha

Conexão é recurso, e todo recurso no React vive num useEffect cujo retorno o desmonta. Sem o stop() no cleanup, navegar entre dois posts deixa a conexão antiga viva: o leitor continua no grupo do post anterior e passa a receber comentário de post que nem está na tela. 

useEffect(() => {
  const conexao = new HubConnectionBuilder()
    .withUrl(`${API_PUBLICA}/hubs/tempo-real`)   // string 1
    .withAutomaticReconnect()
    .build();

  const entrar = () => conexao.invoke("Entrar", postId);   // string 2

  conexao.on("ComentarioCriado", carregar);                // string 3
  conexao.onreconnected(() => { entrar(); carregar(); });
  conexao.start().then(entrar).catch(() => {});   // sem realtime o GET ainda manda

  return () => { conexao.stop().catch(() => {}); };
}, [postId, carregar]);

O catch vazio no start é deliberado e é a diferença entre degradar e quebrar: API fora do ar, rede bloqueando WS, extensão do navegador atrapalhando — a página continua funcionando como sempre funcionou, com o GET e o formulário. Realtime é melhoria, não requisito.

StrictMode em dev monta, desmonta e remonta cada componente. O stop() pode chegar no meio do negotiate e rejeitar — daí o catch também no cleanup. Em produção isso não acontece; o ruído é do modo de desenvolvimento, que existe justamente para expor cleanup ausente.

5. Reconectar não é reentrar

withAutomaticReconnect() devolve a conexão. Não devolve os grupos — e essa distinção é a pegadinha guardada desde a Aula 23: no servidor o grupo é uma lista de ConnectionId, e o ConnectionId muda quando a conexão cai e volta. A conexão reconectada é, para o Hub, um desconhecido.

Por isso o onreconnected faz duas coisas: reinvoca Entrar (senão o resto da sessão é silêncio) e refaz o GET (senão os comentários da janela offline não existem para esta tela). Qualquer uma das duas sozinha deixa um buraco.
