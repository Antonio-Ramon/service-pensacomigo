Typed HttpClient e o Options pattern

Aula 14 · Fatia 14 · Ticket 04 — Imagens (signed URL) · Decisão #14 da arquitetura

Vitória desta aula: POST /api/v1/imagens/url-upload (autenticado) devolve uma URL assinada do Supabase Storage. O front sobe o arquivo direto lá — o binário nunca passa pelo .NET. E de quebra você aprende as duas peças que todo serviço .NET usa pra falar com API externa.

1. O caso de uso, em uma frase

front  ──POST /api/v1/imagens/url-upload──>  nossa API   (só JWT + JSON, leve)
                                                 │
                                                 └─POST /storage/v1/object/upload/sign/…──> Supabase
front  ──PUT {urlAssinada} (bytes da imagem)──────────────────────────────────────────────> Supabase

A API só autoriza e assina. Se o binário passasse por ela, cada upload de 5 MB ocuparia uma thread e a banda do servidor à toa. Isso é a Decisão #14.

2. Problema novo: chamar HTTP de dentro do ASP.NET

Instinto de quem vem de outra linguagem: new HttpClient() dentro do método. Em .NET isso é um bug clássico, e por dois motivos opostos:

JeitoO que quebra
new HttpClient() por chamadacada instância abre socket que fica em TIME_WAIT depois do dispose → esgota as portas sob carga
static HttpClient pra sempreresolve o DNS uma vez e nunca mais → não enxerga mudança de IP do serviço

A resposta do .NET é o IHttpClientFactory: o HttpClient é barato e descartável, mas o HttpMessageHandler por baixo dele fica num pool e é reciclado de tempos em tempos (2 min por padrão). Socket reaproveitado, DNS fresco.

2.1 Typed client: a forma que a gente usa

// Program.cs — registra o serviço E o HttpClient dele, já configurado.
builder.Services.AddHttpClient<IStorage, SupabaseStorage>((sp, http) =>
{
    var cfg = sp.GetRequiredService<IOptions<SupabaseOptions>>().Value;
    http.BaseAddress = new Uri($"{cfg.Url}/storage/v1/");
    http.DefaultRequestHeaders.Authorization = new("Bearer", cfg.ServiceRoleKey);
});

Isso substitui o AddScoped<IStorage, SupabaseStorage> que você escreveria por reflexo — o AddHttpClient<TInterface, TImpl> já registra a implementação e injeta um HttpClient pronto no construtor dela. Base address e header de auth ficam num lugar só, não repetidos em cada método.

Pegadinha da BaseAddress: a barra final importa. Com base …/storage/v1/ e caminho relativo object/upload/… (sem barra inicial) o .NET concatena. Se o caminho começar com /, ele substitui o path da base e você perde o /storage/v1.

3. Options pattern: config vira classe

Até agora a gente leu config assim (JwtTokenGenerator, Fatia 10): 

config.GetSection("Jwt")["Key"]!   string mágica + ! pra calar o compilador

O options pattern troca isso por um POCO ligado a uma seção do appsettings.json: 

public class SupabaseOptions
{
    public string Url { get; set; } = "";
    public string ServiceRoleKey { get; set; } = "";
    public string Bucket { get; set; } = "imagens";
}

// Program.cs
builder.Services.AddOptions<SupabaseOptions>()
    .Bind(builder.Configuration.GetSection("Supabase"))
    .ValidateOnStart();

O ganho de verdade é o ValidateOnStart(): config faltando derruba a aplicação na subida, não às 3h da manhã no primeiro upload. E o handler recebe IOptions<SupabaseOptions> — tipado, sem string mágica, fácil de trocar no teste.

ServiceRoleKey é chave de admin do Supabase — ignora todas as regras de RLS. Vive em user-secrets/variável de ambiente, nunca no appsettings.json comitado (que só guarda a chave vazia) e nunca vai pro front. Por isso quem assina é o backend.

4. Onde cada peça mora (mesma regra da Fatia 10)

Application/Storage/IStorage.cs              o seam — contrato, zero Supabase
Application/Imagens/UrlUpload/…Query.cs      caso de uso + validator + response
Web/Storage/SupabaseOptions.cs               config tipada
Web/Storage/SupabaseStorage.cs               impl: HttpClient + IOptions
Web/Controllers/ImagensController.cs         [Authorize], magro

A Application não sabe o que é Supabase — ela sabe que existe "algo que assina uma URL de upload". Foi assim com IGoogleTokenValidator; é a mesma jogada. É isso que deixa o teste trocar a impl por um fake sem rede nenhuma.

5. Duas decisões de projeto que valem mais que o código

5.1 O path é gerado no servidor

O ticket diz "devolve a signed URL para um path". Tentador: receber o path do cliente. Só que uma URL assinada é uma permissão de escrita — se o cliente escolhe o path, ele pede posts/<id-de-outro-autor>/capa.png e sobrescreve arquivo alheio. Então: 

cliente manda:  { "nomeArquivo": "minha-foto.PNG" }
servidor monta: posts/{usuarioId-da-claim}/{guid}.png

O cliente só influencia a extensão (validada contra uma whitelist). O usuarioId vem da claim sub do JWT, não do corpo. Path traversal deixa de existir porque não existe path do cliente. Fronteira de confiança: nunca confie no caminho que veio de fora.

5.2 É IQuery, não ICommand

Parece escrita ("gerar", "criar"), mas nada é gravado no nosso banco. Marcar como ICommand faria o UnitOfWorkBehavior (Fatia 5) chamar SaveChanges à toa. A regra do nosso CQRS é literal: mudou linha no Postgres? Command. Não mudou? Query. O validator roda igual nos dois — quem o dispara é o ValidationBehavior, não o marcador.

6. A chamada ao Supabase, por dentro

POST {url}/storage/v1/object/upload/sign/{bucket}/{path}
Authorization: Bearer {service_role_key}
{}                                        corpo vazio mesmo

← 200 { "url": "/object/upload/sign/imagens/…?token=eyJ…" }   relativa!

A resposta vem relativa — a URL utilizável é {url}/storage/v1 + isso. Confirmado no código do storage-js (o SDK oficial faz exatamente esse POST). O front depois dá um PUT nessa URL com os bytes.
