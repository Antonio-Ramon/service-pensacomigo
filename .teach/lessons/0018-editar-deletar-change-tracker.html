Editar e deletar: change tracker, dono do recurso e validator genérico

Aula 18 · Fatia 18 · Ticket 05 — Post (fecha o ticket)

Vitória desta aula: o ticket 05 fechou. PUT e DELETE no ar, slug congelado de verdade, e ninguém edita post dos outros. Você escreveu o primeiro handler que não constrói entidade — só muda propriedade e deixa o EF descobrir o resto.

1. Criar constrói; editar muta

Vindo de outra linguagem, a tentação é montar um new Post { ... } com os campos novos e mandar salvar. Em EF Core isso é o caminho errado: você criaria um segundo objeto e o banco ganharia uma segunda linha. O jeito é o oposto — carregar rastreado e mexer no objeto: 

var post = await posts.ObterParaEdicaoAsync(cmd.Id, ct);   sem AsNoTracking

post.Titulo = cmd.Titulo.Trim();
post.TempoLeitura = CalculadoraTempoLeitura.Calcular(cmd.Conteudo);
// não há Update(), não há SaveChanges() aqui

Não tem posts.Atualizar(post) porque não precisa. O change tracker (aula 16) guardou uma foto do objeto no momento em que ele saiu do banco; no SaveChanges — que quem chama é o UnitOfWorkBehavior, no fim do pipeline — ele compara foto e objeto e emite um UPDATE só com as colunas que mudaram. É por isso que ObterParaEdicaoAsync é o segundo método do repositório sem AsNoTracking: sem rastreio não há foto, e sem foto não há diff.

2. A coleção N:N: trocar a lista inteira

public Task<Post?> ObterParaEdicaoAsync(Guid id, CancellationToken ct = default) =>
    db.Posts.Include(p => p.Tags).FirstOrDefaultAsync(p => p.Id == id, ct);

// no handler:
post.Tags = vinculadas;

Uma linha, e o EF emite o DELETE das tags que saíram e o INSERT das que entraram em post_tags — nada mais. Mas isso só funciona por causa do Include(p => p.Tags): o EF só sabe remover o que ele carregou. Sem o Include, a coleção original chega vazia, o diff vira "só inserções" e as tags antigas ficam grudadas no post para sempre. Esse é o bug clássico de edição N:N.

3. Slug congelado: a regra que se cumpre por omissão

O EditarPostCommand aceita título novo — e o handler não toca no post.Slug. Nenhum if, nenhuma validação: a regra "o slug nasce do título e congela" virou uma linha que simplesmente não existe. Note também que o EditarPostRequest não tem campo Slug; se tivesse, um cliente conseguiria renomear a URL de um post já compartilhado por aí. Campo que não existe no DTO é a validação mais barata que há.

4. Dono do recurso: por que 404 e não 403

if (post is null || post.AutorId != cmd.AutorId)
    throw new NaoEncontradoException("Post", cmd.Id.ToString());

As duas condições caem na mesma exceção de propósito. Um 403 Forbidden seria tecnicamente mais preciso — mas ele responde "esse post existe, só não é seu", e com isso qualquer um enumera Ids até mapear o acervo alheio. O 404 não distingue "não existe" de "não é seu", e é exatamente essa a intenção. Repare onde a checagem mora: no handler, não no [Authorize]. O atributo responde "quem é você?"; "isso é seu?" é regra de negócio, e regra de negócio fica na Application.

5. O validator genérico

Criar e editar cobram exatamente as mesmas regras de corpo (título, capa, blocos coerentes). Em vez de duplicar as quatro regras, uma interface descreve o formato e o validator fica genérico nela: 

public interface IPostEscrita
{
    string Titulo { get; }  string ImagemCapa { get; }  List<Bloco> Conteudo { get; }
}

public abstract class PostEscritaValidator<T> : AbstractValidator<T> where T : IPostEscrita { ... }

public class CriarPostCommandValidator  : PostEscritaValidator<CriarPostCommand>;
public class EditarPostCommandValidator : PostEscritaValidator<EditarPostCommand>;

Duas coisas específicas de C#/.NET aqui. Primeira: record implementa interface de propriedades de graça — os parâmetros posicionais já geram as get exigidas, sem escrever nada. Segunda: o AddValidatorsFromAssembly varre o assembly procurando classes concretas; ele ignora a genérica aberta PostEscritaValidator<T> (abstrata) e acha as duas fechadas. Por isso as subclasses de uma linha precisam existir — elas são o que o scanner consegue instanciar.

6. Deletar: o banco faz o trabalho

posts.Remover(post);   → db.Posts.Remove(post)

Nenhuma linha apaga comentários, likes ou post_tags. O schema já declarou OnDelete(DeleteBehavior.Cascade) nessas FKs, então o Postgres derruba os filhos junto. A tag sobrevive — a cascata segue a junção, não o outro lado do N:N (senão deletar um post apagaria a tag "Meditação" do site inteiro). O teste de integração afirma exatamente isso.

E o verbo devolve 204 No Content, não 200 com corpo: não há o que devolver. No MediatR, "sem resposta" ainda precisa de um tipo — daí o ICommand<Unit>, com Unit fazendo o papel de void.
